## 1. 产品定义与核心判断

面向跨境货代、中小外贸团队及单证审核人员，提供一个以对话为入口的单票多文件处理工作区。用户上传商业发票、装箱单、提单等材料，系统提取并核对关键字段，完成有来源的翻译和目标语言译本生成，由人确认后导出可编辑译本及审核结果。

产品价值是缩短单票单证整理与复核时间，降低由单证错漏造成的返工风险。竞品已有 OCR、翻译和跨单证核对能力，因此我们的可验证重点应是：**聊天发起简单、每个重要结论可回看原文、真实冲突不会被静默修平、复核后能按版本稳定导出**。本产品不承诺自动保证通关、单证真实性或法规结论正确。

### 1.1 三层职责

| 层 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 对话主体（外层 Agent） | 理解用户意图、选择允许的业务入口、提出缺少的业务参数、汇报任务状态、基于已落库证据回答问题 | 不直接阅读整份原件后自行生成最终字段、金额或单证；不替用户裁定冲突；不绕过审核直接导出 |
| 单证工作流 | 文件接收、解析/OCR、分类、字段抽取、标准化、规则核对、受控翻译、目标语言译本排版、输出回检、版本管理；统一模板制单留待后续扩展 | 不依赖外层对话的临时记忆保存业务事实 |
| 复核与证据层 | 保存原件、字段来源、问题与裁定、译前译后版本、任务事件和导出快照；向对话与界面提供只读查询 | 不把低置信度候选自动写成“已确认事实” |

外层模型可调用 `create_case`、`start_document_workflow`、`get_task_status`、`get_run_timeline`、`query_case_facts`、`query_provenance`、`list_issues` 等受控业务工具。上传后的原始文件直接交给单证工作流；外层模型可按需查询全流程的阶段事件、问题、字段和来源，但每次只读取与提问有关的授权片段，不将原件全文灌入对话上下文。处理工作流本身可使用 OCR、视觉、抽取和翻译模型；“外层不参与单证处理”不等于整个系统完全不用模型。

### 1.2 业务基本单位

- **单票（Case）：** 一次货运/贸易业务的工作空间。包含多份源单据、处理任务、问题、修订、对话关联和导出记录。归票不确定时由用户确认。
- **源文件（Source Document）：** 用户上传的原始 PDF、图片或 DOCX。原件不可覆盖，保存哈希、上传时间、文件格式和 `document_version`；用户上传替换原件才新增 DocumentVersion，重复解析同一原件不改变它的版本。
- **解析版本（Parse Artifact）：** 同一 DocumentVersion 的每次有效解析结果以不可覆盖的 `parse_artifact_id` 标识，保留所用引擎和配置；重新解析可以产生新解析版本，旧来源与历史交付仍指向旧解析版本。
- **逻辑单据与区段（Logical Document/Document Section）：** 解析成功后，源文件内可独立分类和核对的逻辑单据有 `logical_document_id` 和类型；它包含一个或多个带 `section_id`、原件页／区域范围和顺序的区段，均归属于确定的 `parse_artifact_id`。未解析文件可暂时没有逻辑单据。混合 PDF 中的发票与箱单分别建逻辑单据、分别抽字段和运行适用规则，但导出仍按源文件生成一组译本。
- **处理任务（Run）：** 对某个单票按固定 Task Spec 执行的一次工作流任务；安全重试和不改变任务范围的局部重算记在该 Run 的事件与版本链中，更换目标语言、参与文件或翻译范围另建 Run。首版至少有只读“识别/索引”和“翻译校验”两种模式，共用解析产物；前者回答新上传文件的内容问题且不需要目标语言。任务可暂停、失败、恢复，并持续产生日志事件。
- **上传会话（Upload Session）：** 在选中文件并开始上传时生成，记录逐文件进度与失败原因；成功文件归入草稿 Case，至少有一份文件成功且任务要求明确后才创建处理任务。
- **工作版本（Revision）：** 首次建立结构化字段时形成 Case 的基线业务 `revision_id`，候选字段仍标待复核，不因有版本就视为人工确认；后续字段与裁定形成 Case 内新的业务版本。译文形成所属 Run／目标语言内唯一的 `translation_revision_id`；两类版本不可覆盖。仅上传或仅解析原件时可以尚无业务版本。每份译文记录所依据的业务版本和解析版本；新增另一种语言不覆盖已有译文，来源事实变化时仅使依赖它的译文失效。引用和导出须同时固定 Case、Run、语言、相关原件及解析版本、业务版本和实际使用的译文版本。
- **导出快照（Export Snapshot）：** 对某个已确认版本完成生成与回检的一组交付文件清单。默认每份参与的源单据对应目标语言 DOCX 和 PDF 各一份，另可选逐源识别稿 PDF；文件清单记录各原件版本、解析版本和译文版本到导出文件的映射，与处理中预览稿严格区分。

一票可有多次任务，一次任务可处理多份源单据。聊天会话是交互入口，可关联单票，但不能代替单票和文件版本本身。

## 2. 用户、场景与首版边界

| 角色 | 常见目标 | 必须看到的结果 |
| --- | --- | --- |
| 单证操作员 | 快速录入、核对并转换一票材料 | 待办、原文位置、可编辑字段、可导出稿 |
| 业务复核人 | 判断冲突和译文是否可接受 | 同票对照、问题原因、修改记录、确认人 |
| 主管/团队成员（后续多用户） | 查询历史处理情况与复用资料 | 权限范围内的任务、版本、导出记录与来源引用 |

典型场景：客户一次上传拍照装箱单、PDF 发票、DOCX 补充材料，说明译成英文；系统识别单证类型和内容，发现箱单与发票数量冲突；用户在侧边审核区点击红框查看两份原文并裁定，系统只重算受影响的字段、翻译和输出；用户确认后导出目标语言译本，在管理台可按文件名、日期、类型找回，并在聊天中通过 `@ ` 关联该单票询问“为什么当时修改了数量”。

**建议首版范围：** 中文/英文；商业发票、装箱单、提单三类核心材料，以及标记为“其他佐证材料”的补充文件；图片、原生/扫描/混合 PDF、DOCX；同票多文件；关键主体、编号、货描、数量、单价/总额、币种、件/箱数、毛重/净重、日期、起讫地、运输信息；以翻译工作流为首要闭环，交付双语对照译本、异常报告和通过回检的 DOCX/PDF。统一模板的商业发票/装箱单制作为后续扩展。其他佐证材料可解析、检索和供人工引用，但只有审核人明确指定其字段角色和关联对象后才参与跨单证规则，不由模型擅自把它当发票或提单。来源国、目的国、贸易术语等缺失时仍可解析，但依赖它们的规则显示“无法判断”。

EDI 在赛题中被明确提及，但与 PDF/OCR 是另一条解析路线。建议放到后续行业深化阶段，先选一个确定的 EDI 标准、版本和报文类型做 schema 映射，不用 OCR 处理 EDI，也不宣称支持所有 EDI。全国家法规、自动 HS 最终归类、真实海关申报、承运人提单重签发、原版式任意文件重建和全自动无人工审核均不纳入首版承诺。

首版通用识别、翻译、来源追溯和有明确前提的单据内／跨单据一致性检查，不按某一贸易线路或货类硬编码；验证样本按多线路、多货类、双向中英、多格式和异常边界做成小规模覆盖矩阵。线路或货物专属法规结论只能在权威依据、适用条件、有效期和审核人均确认后启用；首批受控规则样本先选中国出口至欧盟的一般非危险消费品，其他线路和特殊货类仍可走通用流程，但专项法规显示“未覆盖／无法判断”，不得被说成合规通过。

## 3. 界面信息架构

首版建议做**桌面优先的 Web 应用**，实现类似桌面 Agent 的交互布局；后续如需本地安装，可在稳定后封装为桌面客户端。这个选择减少首版跨平台安装、自动更新和本地文件权限成本，不改变用户看到的对话主体形态。

| 区域 | 默认内容 | 关键入口 |
| --- | --- | --- |
| 左侧导航 | 新对话、会话列表、单据管理台、技能与 MCP、设置 | 回到历史会话、按任务打开单票 |
| 中央对话区 | 带用户/Agent 头像的消息流、欢迎引导、聊天框上方的**“单据翻译与转换”主卡片**、上传区、进度卡片、结束服务卡片 | 文字输入、拖拽/选择多文件、`/ `、`@ ` |
| 右侧复核区 | 默认收起；处理结果可用时由任务卡片打开，可拖动宽度 | 原件、字段问题、译文/目标稿三种视图与联动对照 |
| 单据管理台 | 默认已导出的 Run 处理批次列表，可展开多份原件与译本；其他状态与按单票汇总可切换 | 按日期、来源地、收件人、处理人检索；打开原件、校验页与历史快照 |
| Skill 与 MCP 仓库 | 轻量列表、能力说明、启用与连接状态 | 创建/导入 Skill，新增 MCP 接入配置，测试连接、停用、删除 |

主卡片应明确展示“上传一票材料 → 自动识别与核对 → 人工复核 → 导出”。它有上传按钮和示例入口，点击可先进入向导；直接把文件拖入对话框则进入同一向导。卡片不是第二套处理逻辑，两条入口最终都创建同一类 Case/Run。用户主动结束服务后展示结束卡片；下次默认新建会话，已结束会话只供查看，继续处理旧票时须在新会话显式关联该 Case。

右侧复核区适合 13 英寸以上桌面屏幕。窄屏或窗口过小时切换为全屏复核页，保持所有原文与译文可访问；不要求在狭窄侧栏内强行展示三栏。宽度由用户拖动并记住偏好，复核状态与所选字段可在刷新后恢复。

## 4. 从对话到交付的完整用户流程

1. **发起与澄清。** 用户点击“单据翻译与转换”卡片、上传附件，或输入“把这票发票和箱单翻成英文并核对”。对话主体先判断是翻译、识别、查询还是其他任务。翻译意图、目标语言、文件范围或归票关系不明确时追问；标准交付物为界面明示的目标语言译本与报告，用户没有特殊输出要求时不因此阻断 Run。若只问新上传文件内容、尚无解析产物，则路由到只读“识别/索引”Run，不要求翻译目标语言。
2. **上传与建票。** 用户开始上传时建立草稿 Case 与 Upload Session，前端显示每个文件的上传进度、格式与大小检查。成功文件成为该 Case 的原件；全部失败则保留可重试的上传会话并按保留策略清理空草稿 Case。部分失败时列出缺失材料。重复文件给出提示，不悄悄丢弃。无法确定归票时暂停等待用户分组。至少有一份上传成功，且对应模式的必需条件明确后，才由路由 Skill 建立处理 Run。
3. **后台处理。** 翻译工作流逐文件解析/OCR，划分文件内逻辑单据并识别类型，按节提取字段及原文锚点，汇总到同票，完成内部与跨单证校验，再生成带来源的译文草稿。前端按实际事件连续显示阶段、当前文件、完成数量与问题摘要。
4. **复核前预览。** 系统生成可读 Markdown 副本、结构化字段和译文草稿。低质量、字段冲突与未覆盖规则以待复核或无法判断显示；不把草稿标为已通过。用户可在聊天卡片点击“查看并校验”。
5. **人工校验。** 右侧复核区对照原件、字段/异常和目标语言译本预览。点击问题定位原文与译文；修改字段或裁定事实时记录理由并产生新业务 `revision_id`，只让依赖它的校验、译文及预览失效；纯译文修订只增加该 Run/语言的 `translation_revision_id` 并重做相关翻译 QA 与预览。首版不重复运行未受影响的 OCR。关键问题未处理时，导出“确认稿”不可用；可按权限下载带明显草稿标识的预览供讨论。
6. **最终导出。** 系统冻结当前确认版本，默认按参与处理的每份源单据分别生成纯目标语言 DOCX 和 PDF，可选逐源识别稿 PDF；用户可在任务摘要中调整译本的已支持格式。每个译本都能回指源文件版本；同一混合 PDF 仍是一份源文件，对应一份内部分节的译本。整组文件检查字段覆盖、数值、可抽取文本与版面，全部成功后才原子登记一份导出快照和管理台“已导出文件”。浏览器下载中断可重试，不影响已经成功生成的快照。
7. **复用。** 用户在管理台找回单票，查看原始文件、任务时间线、修改记录和所有成功导出快照；在聊天中输入 `@ ` 并选择单票、处理批次、原件或成功快照，提问并跳转至被引用的原文。选择 Case 的“当前版本”时，在发送消息时解析并记录当时的具体业务版本；选择固定原件版本或导出快照时始终指向所选版本。选择 Run 时固定该批次及参与的原件版本，询问“导出结果”默认引用发送时该 Run 最近一次成功快照并明示其时间，旧稿须选择对应快照。

用户可以取消排队中的任务，也可在安全边界内取消运行中的任务；取消不删除已上传原件或已有已导出快照。首版支持页面刷新后从持久化阶段查看任务；进程重启后，可安全确认的未完成步骤自动续跑，收费外部任务的提交结果无法确认时暂停自动重投并进入人工核查。幂等、供应商任务 ID 和步骤账本从首版建立，后续阶段再扩展更多故障场景的自动处理。

## 5. 对话主体的能力与边界

### 5.1 支持的提问

- 领域知识问答：解释提单、装箱单、毛重/净重、Incoterms 等概念；涉及法规或目的国要求时必须说明来源、适用范围与更新时间，没有已审核规则时只作一般解释。
- 当前任务问答：“现在到哪一步”“为什么卡住”“哪些字段待确认”“这处为什么标红”。回答从任务事件、字段和规则结果读取。
- 单证事实问答：“这票总金额是多少”“箱单与提单重量一致吗”“第 3 行货描译成了什么”。已有解析结果时只读查询；新上传文件还没解析时可启动共享解析能力的“识别/索引”Run，再根据结果回答，不要求用户改成翻译任务。回答给出值、状态和可点击来源；冲突时并列列出，不任选一个值。
- 历史问答：通过 `@ ` 选择单票时默认指向当前有效业务版本，并在发送时冻结本轮具体版本；也可选择处理 Run、某份原件的固定版本或成功导出快照。回答旧版问题时标明它与当前版的关系，不将旧值误写为最新事实。
- 操作引导：创建处理任务、打开复核区、定位字段、发起重识别（首版按文件，后续可按页/行）。修改事实、重跑有费用的步骤和正式导出走业务操作接口与相应确认，不靠模型一句话直接完成。

### 5.2 对话回复规则

单证问答不套固定句式，但必须表达结论或无法确认的状态、相关依据及版本，并在需要时给出下一步。界面将引用呈现为带原文摘录、文件名、页码/段落和版本的证据卡；点击卡片打开右侧校验页并定位对应位置。示例：“目前不能确认毛重一致：装箱单为 1,250 kg，提单为 1,205 kg，相差 45 kg。请复核两处原文。”其后展示两张来源卡。数值运算由程序完成，模型负责理解问题和组织表达。若人工裁定值与原文不同，回答必须分别展示“原文写的是……”与“复核人依据……确认使用……”，不能用原文锚点假装证明人工改值。

对话主体读取的是带权限、单票 ID、文件 ID、版本和来源锚点的只读业务视图。原件中出现“忽略以前指令”之类文字只作为单证内容，不可变为系统命令。不能根据聊天历史覆盖最新已确认字段。查无依据、规则不覆盖或来源不可靠时提示无法核实/待确认。对话范围采用宽松的业务关联判断：物流、单证、系统操作及理解当前材料所需的技术、合同、财务、公式等补充知识均可解释，不按学科关键词拒答。连续追问结合本会话安全语境；仅对明确无关的独立请求简短引导，不结束会话或修改现有任务。答复目标为实际模型正文增量可见、生成期间直接显示已收到正文而不显示待核验标签或占位提示、最终证据核验后定稿；详细约束及当前未实施状态以对话产品设计与最终补全修复方案为准。

### 5.3 `/ ` 与 `@ ` 的交互

- 用户输入 `/` 后紧接一个空格（`/ `）时弹出可用技能和 MCP 工具，支持名称/描述搜索、键盘选择、显示工具用途与所需权限。选中后在输入框显示结构化引用，发送时由路由器调用对应能力；未安装或无权使用的扩展不出现。
- 用户输入 `@` 后紧接一个空格（`@ `）时弹出单票、处理 Run、原件和成功导出快照的选择器，支持按文件名、日期、类型与摘要搜索；选择单票或 Run 的工作版时按发送时状态冻结，选择导出快照时总是固定其历史版本。发送消息时将指针解析为稳定 ID 和具体版本，写入该条消息的引用记录，而不是只把文件名写进提示词。回答引用必须回指本轮解析出的版本；后续版本变化时提示旧回答所用版本。
- `@ `某个源文件版本只固定原件；它可能有多个目标语言和处理 Revision。问“译成了什么”时优先使用本会话活动任务的目标语言与最新有效译文；没有活动目标且存在多份有效译文时让用户选择语言或快照，不混合不同 Run 的译文。`@ `导出快照始终读取它冻结的译文。
- 用户同时使用 `/ ` 与 `@ ` 时，先解析目标对象、所属关系、版本和权限，再让技能或 MCP 工具读取获准的最小范围。首版一个活动会话只绑定一个 Case；跨票比较暂不开放，后续如增加此能力，必须让用户逐票明确范围和授权。

### 5.4 对话记忆与会话隔离

系统提示词及工具边界是开发方维护的版本化系统记忆，用户不可直接修改。可跨会话读取的用户记忆仅包含当前用户明确保存的稳定偏好；单票/文件/处理记忆来自有版本与来源的业务数据，仅在当前上传或 `@ ` 关联时加载。当前会话最多保留最近 20 轮用户与 Agent 对话；更早内容压缩为**只在本会话有效**的摘要。结束服务卡片关闭本会话，下一次默认新对话，既不加载旧消息，也不加载旧会话摘要。不同用户及团队的数据在检索前按身份、单票和版本过滤；即使首版是单用户演示，存储和查询也必须具备明确的 owner 边界。详细规则见[对话工作台与对话 Agent 详细设计](对话工作台与对话Agent_产品设计.md)。

## 6. 独立单证工作流

用户设想的“PDF/图片/Word → Markdown → 信息提取 → 翻译 → 新单据”可作为人可读的流程展示，但底层不能让 Markdown 成为唯一事实来源。合并表格、行项目、坐标、原文与版本都需要结构化保存。建议采用以下阶段；其中某些轻量步骤可在同一个服务中执行，不要求拆成许多进程。

| 阶段 | 输入与动作 | 主要产物 | 失败/复核策略 |
| --- | --- | --- | --- |
| 0 接收与检查 | 校验文件类型、大小、页数、哈希、权限，关联单票 | 原件与文件元数据 | 格式不支持、损坏或文件过大时逐文件报错，其他文件可继续 |
| 1 类型识别与预处理 | 按页／区域识别发票、箱单、提单或其他佐证材料的逻辑边界，检测图片清晰度、PDF 文字层与混合页 | 文件内逻辑单据与区段 ID、类型、页／区域范围、页面质量、处理路线 | 无法识别边界或类型时建立未分类节并请用户指定；低清晰度请求重拍 |
| 2 解析与 OCR | DOCX/可用 PDF 文字层优先原生解析；扫描页或嵌入图使用 OCR；保留表格结构、位置及所属逻辑单据 | 原始解析结果、块/表/行、页/段落/单元格锚点、Markdown 阅读副本 | 单页失败标记具体页；首版可重试该文件，第二阶段再做按页重识别；原文不可读不凭空补字 |
| 3 字段抽取与规范化 | 按逻辑单据类型映射统一字段 schema，保留原值、单位、候选值、来源和置信线索 | 带逻辑单据与区段 ID 的字段与明细行版本 | 数字、箱号、HS 等关键字段低可信时待复核 |
| 4 业务校验 | 按逻辑单据执行必填/格式与金额计算，明确跨节、跨文件关系后核对主体、数量和重量，再运行有限规则包 | 带节归属的错误、疑点、无法判断清单 | 冲突不自动选择“正确值”；缺参数不推断合规通过 |
| 5 受控翻译与预览 | 翻译已确认字段；待复核字段仅生成明确标记的临时译文；保护金额、编号、日期、单位及术语，按当前字段生成非正式双语预览 | 译文草稿、术语 QA、源译对照、转换预览 | 高风险字段未确认时不得转为正式译文；草稿预览不能被当作确认稿 |
| 6 审核与修订 | 人工看原文、比较多单据、裁定问题、修改字段/译文并签名留痕 | 新工作版本、裁定记录 | 按依赖重算受影响步骤；未解决问题保持待办 |
| 7 译本排版与输出回检 | 将确认字段和译文写入源布局驱动的纯目标语言译本；混合文件按逻辑单据分节，但仍按源文件生成 DOCX/PDF，检查字段、排版与文本层 | 逐源文件目标语言译本与所选逐源识别稿 PDF | 回检失败保留任务与错误，不形成成功导出快照 |

文件接收属于阶段 0 的 Upload Session；“识别/索引”Run 在成功上传后执行阶段 1—3 的分类、解析和字段建立，供新上传文件的事实问答，不进入翻译、复核导出阶段，也不要求目标语言。之后启动翻译 Run 时复用同一原件版本、解析版本与配置下仍有效的产物；翻译 Run 则走完整链路。先决定事实，再决定正式译文和输出；为了提前提供侧边对照，阶段 5 可基于尚待确认的字段生成带“待确认”标记的临时译文及双语预览。这是供用户发现问题的草稿，不满足导出确认稿条件。来源事实一旦修正，受影响的旧译文与旧预览必须失效。原始文件始终只读；修订的是系统字段值，不改写原件。

字段示例需至少保存：`case_id`、`document_id`、`document_version`、`parse_artifact_id`、`logical_document_id`、`section_id`、`field_key`、`raw_text`、`normalized_value`、`unit`、`source_anchor`、`review_status`、`rule_version`、`modified_by`、`modified_at`。人工修订另存 `asserted_value`、裁定理由和依据来源；译文按所属 Run／语言及译文版本另存。`raw_text` 与原件锚点不可覆盖。金额用十进制定点；HS、税号、箱号按字符串保存前导零。PDF/图片的锚点可以是页号与矩形坐标，DOCX 优先用段落/表格/单元格定位；预览 PDF 的页码只属于其对应的渲染版本。解析器没有坐标时显示“无法精确定位”，不猜位置。

明细行需有在所属 `document_version + parse_artifact_id` 内稳定的 `line_item_id`、`logical_document_id`、`section_id`、行序号、原文锚点、货描、数量/单位、单价、金额等字段，以及可选的商品编码和包装层级。跨单证匹配单独保存关联 ID、两侧行 ID、匹配依据与人工确认状态；允许“一行发票对应多箱装箱明细”“多行商品合并到一份提单”这类一对多/多对一关系，不以行号相等或货描字符串相同作为唯一依据。重新解析同一原件产生新 `parse_artifact_id`，替换上传才产生新 `document_version`；两种情况下旧／新区段和行 ID 都须映射或标为待复核，旧匹配不得直接套用。

校验不能退化为相同字符串比较：提单 `Shipper` 与发票 `Seller` 可能合理不同，毛重与净重不能比较相等，箱数与件数口径不同，原产国与发货国不同。每条规则须写明适用单证、输入字段、比较口径、严重程度、版本与依据。目的国规则仅启用经过核验的有限规则包；HS 先做格式和已有货描/编码的风险提示，不做自动归类结论。

## 7. 流式进度、任务状态与异常处理

“流式”指后台在任务过程中持续发送**真实阶段事件**，不是让对话模型编写一段看似正在处理的文字。可用服务端事件流（SSE）把持久化事件推送到前端；断线重连按递增事件序号补齐。长任务由后台任务执行器运行，不能依赖浏览器标签页持续打开。上传阶段用 Upload Session 事件，开始处理后用 Run 事件；聊天消息中的进度卡片和单据管理台使用同一状态源。

| 状态 | 前端文案示例 | 用户可做什么 |
| --- | --- | --- |
| `uploading` | 正在上传 2/3 份文件，当前为装箱单.pdf | 查看逐文件进度、取消未完成上传 |
| `queued` | 上传完成，正在等待处理 | 返回其他页面，稍后查看 |
| `classifying` / `parsing` | 正在识别文件类型；正在解析第 2/4 页 | 查看当前文件与页数；错误时查看原因 |
| `extracting` / `validating` | 正在提取关键字段；正在核对发票与箱单 | 查看已完成的文件与初步结果 |
| `translating` / `rendering` | 正在生成译文草稿；正在准备输出预览 | 可查看已完成阶段，不提前标“已导出” |
| `awaiting_review` | 发现 2 项需确认，请打开复核区 | 人工裁定、补充材料、局部重跑 |
| `ready_to_export` | 复核完成，可以生成确认稿 | 点击导出并选择已支持的目标语言译本格式 |
| `exporting` / `exported` | 正在生成并回检；已生成可下载文件 | 下载、查看版本与审核记录 |
| `failed` / `cancelled` | 处理未完成：第 3 页无法识别；任务已取消 | 查看失败文件、修复后恢复或重新发起 |

**进度展示规则：** 每个事件包含 `case_id`、`operation_id`（上传时为 `upload_id`，处理时为 `run_id`）、该操作内的递增序号、时间、阶段、文件/页范围、状态、可见说明和可选计数。百分比只在分母已知且可测时显示，例如上传字节、已处理页数；模型抽取和法规核对不虚构“87%”。上传另计，Run 可用“已完成 3/7 个处理阶段”的粗粒度进度。阶段结束时立即持久化结果，再推送完成事件；重复事件不会导致重复 UI 项。

**异常分类：** 上传/格式错误、解析或 OCR 不可读、外部服务暂时故障、服务额度不足、业务材料冲突、翻译 QA 失败、模板回检失败分别给出不同提示与下一步。网络故障按幂等键和供应商任务 ID 安全重试；低清图片要求重拍或人工确认；材料冲突必须人工裁定；导出布局错误只重生成输出。首版页面刷新和服务进程重启后都从数据库恢复展示；可确认的未完成步骤自动续跑，收费接口提交状态无法确认时停止自动重试并提示人工核查。自动内容修复设置有限轮次，未得到新证据时停止循环。

## 8. 复核工作区：侧栏如何让用户真正确认

用户从任务卡片或管理台点击“查看并校验”打开可拖动的右侧工作区。默认优先显示待处理问题；问题数、严重度和“无法判断”数分开计数。右侧可切换三种布局：

1. **原文/译文并排：** 左边是原 PDF/图片/DOCX 渲染预览，右边是翻译或转换预览，适合检查版式、漏译和关键数据。
2. **字段/证据并排：** 左边是单据结构化字段与同票差异，右边定位到来源原文，适合判断数量、重量、主体和日期。
3. **三栏宽屏：** 原文、字段问题、目标稿同屏，适合大屏复核；窄屏自动切回双栏或标签页。

右侧区显示源文件名、可切换的逻辑单据节及其页／区域范围、单据类型、原/目标语言、主体角色（发货方、收货方、通知方、卖方等按单证类型区分）、运输信息（起运地、目的地、船名/航次或运单号）、货物与金额等字段。字段按“基础信息—主体—运输—货物/明细—费用与金额—语言与译文—风险问题”分组；只展示与当前逻辑单据相关的分组，不把混合文件中的多个类型硬塞进同一张表。

点击字段高亮原文位置，并同步定位到译文/目标稿对应位置。**红框只表示高风险问题或事实冲突**，橙色表示待确认，蓝色表示当前选中，绿色表示已确认；配图标和文字，避免只依赖颜色。坐标缺失时跳到最近的页、段落或表格并说明无法精确框选。对多文件冲突同时展示两个来源的原值、单位、规则理由和各自的点击跳转，不让系统悄悄挑选一个。

用户可逐字段执行：确认无误、编辑系统识别值、编辑译文、标记暂无法判断、申请重识别（首版按文件，后续支持页/行）、上传补充材料。修改须保留原文值、人工采用值、操作者、时间、原因及补充依据，生成新版本；原文定位只证明原件写了什么，不证明人工改值正确。系统展示受影响的规则、译文、摘要与目标稿，然后重算相关依赖。对“忽略此问题”也应记录理由与权限，高风险冲突不能靠忽略变成自动通过。审核区要区分“识别错误”“原件确实冲突”“翻译问题”“资料缺失”“规则不适用”五类处置。

| 问题/处置 | 确认稿导出 | 界面与审核记录要求 |
| --- | --- | --- |
| 高风险事实冲突、必填缺失、来源不可读或数字被改写，仍未解决 | 阻断 | 只能查看或下载带草稿标识的预览；列出两个来源和待办 |
| 审核人依据补充材料或可核查原文完成裁定，受影响校验与译文 QA 已重算 | 按规则允许 | 原始冲突结论仍保留；另存人工处置与是否解除交付阻断，记录原文值、采用值、裁定理由和确认人 |
| 一般提示已核查并确认可接受 | 允许 | 审核记录保留提示与确认记录，不伪装为“无异常” |
| 规则确实不适用，有明确条件及复核理由 | 允许 | 标记“不适用”及依据，不计作自动通过 |
| 目的国规则未覆盖或缺少适用前提 | 允许导出翻译/整理稿，不允许标“合规通过” | 审核记录显著注明“合规未评估/无法判断”，不得给出自动放行结论 |

首版单用户演示由当前登录的复核人确认并留名；未来多用户场景再按角色配置裁定与例外权限。即使业务人员希望带问题交付，也只能下载明确标注未解决问题的草稿，不能生成“已审核确认稿”。

原始规则结果、人工裁定结果和“是否阻断确认稿”分别存储。规则重算后原件仍然矛盾，不应把原始红项篡改成“规则通过”；只要裁定有可核查依据、操作者有权限、所依赖的译文与输出检查完成，可将**交付阻断**解除并在审核记录显著保留原始冲突与采用值。没有依据、越权或重算未完成的裁定继续阻断。

“确认并导出”前展示确认清单：还有哪些阻断问题、哪些只是提示、采用哪份原值/修订值、目标语言与模板、导出后的文件名。用户确认的是**当前业务版本与逐文件译文版本的有效配对**，未改变的译文可凭经验证的兼容记录配对新业务版。复核完成产生绑定清单、版本、确认人和时间的不可变确认记录；导出开始和登记快照时都重新核对它。后续关键字段或译文变化后，受影响范围须重新审核并生成新快照。不能在界面显示“审核通过”却继续引用旧译文或旧规则结果。

## 9. 转换结果与导出定义

| 结果 | 首版用途 | 保存规则 |
| --- | --- | --- |
| Markdown 阅读副本 | 辅助检索、可读预览和模型上下文，不是唯一事实层 | 与解析版本关联，供内部使用 |
| 结构化字段与异常记录 | 审核、对话引用和后续系统对接 | 每次工作版本可追溯；审核记录须含来源、规则及未解决项 |
| 双语对照预览 | 审核原文与译文，检查数字和术语 | 处理中草稿可重建；明显标记“待确认/草稿” |
| 每份源文件的目标语言译本与所选识别稿 PDF | 每份参与处理的源 Document Version 各对应一份 DOCX/PDF 译本，另有所选逐源识别稿 PDF | 首版正式交付；整组由服务端生成并回检成功后建立导出快照 |
| 统一模板电子稿 | 基于确认字段制作商业发票/装箱单 | 后续扩展；与翻译件区分，不冒充重新签发的原件 |
| 提单等承运人单据 | 原文证据与译本/业务摘要 | 不生成看似承运人重新签发的有效正本 |

导出时先冻结业务版本、逐文件有效的解析与译文版本、模板版本、规则版本与目标语言，按每份参与的源文件生成暂存译本，再生成可选的逐源识别稿 PDF；快照文件清单记录 `document_version + parse_artifact_id + run_id + target_language + translation_revision_id → output_artifact` 映射。做机器可检查的字段覆盖、行项目数值、译文中的编号/金额保护、DOCX/PDF 文本可抽取性及页面越界检查。必要时人工查看长表和复杂布局。整组全部通过后原子地登记为 `exported`，附生成时间、确认人、文件哈希、模板和来源版本；任一必需译本失败时整组不登记成功快照。审核记录对人工修订同时列出原文值、采用值、理由与补充依据；原文锚点不能被解释为修订值的证明。失败产物只作为短期内部诊断/预览，不出现在用户管理台的“转换后文件”列表。

**“只保留成功导出的转换后文件”的精确定义：** 原始文件、任务、字段修订和问题历史在单票有效期内保存，不因一次导出失败而删除；转换中的预览稿不作为正式历史文件。只有服务端完成生成与回检的文件进入导出快照。成功生成后用户下载失败，可重新下载同一快照；若之后又修订，原快照在有效期内仍可审计，当前版本标记为需重新导出。整票 Case 自最后一次实质性业务变更起保留 30 天；到期自动删除，Case 所有人也可在管理台主动申请删除该票，申请生效后该票立即不可读并进入后台物理清理。取消单个 Run、撤销任务草稿与删除整票是不同操作；详细的计时、清理范围和页面反馈见[单据管理台产品设计](单据管理台_产品设计.md)第 7.2 节。

## 10. 单据管理台与历史检索

管理台默认按**已成功导出的翻译 Run** 展示处理批次列表，一行是一轮有明确输入范围和处理人的任务，可展开多份源文件、文件内逻辑单据、逐文件目标语言译本及该 Run 的成功 Export Snapshot。同一 Case 在不同语言或重处理的多次 Run 中可出现多行；点击 Case 标识进入聚合这些记录的单票概览。列表以导出时间倒序显示单票名、批次、目标语言、源文件数、问题数、任务发起人、导出时间和快照版本。待复核、处理中、失败或取消的 Run 留在其他状态筛选及任务历史中；只有成功快照中的产物进入正式“转换后文件”列表，原件始终保留。

筛选支持日期区间（默认导出时间，另可选上传、处理发起、最近活动或复核时间）、文件名、逻辑单据类型、任务状态、目标语言、来源地、收件人、处理人和单票编号。来源地默认查原件明确给出的货运起运地；承运人接货地、装货港和原产国／地区是另外的字段角色，不能从发货人地址或其他地点猜测起运地。收件人按单据角色区分 Consignee、Buyer 等，冲突值并列为候选。处理人默认任务发起人，复核人和导出确认人作为可选角色；搜索按用户 ID 与有权限的显示名匹配。语言条件按 Run 或 Export Snapshot 命中，不读取 Case 上一个可被覆盖的语言字段；界面明确“仅当前结果／包含历史快照”的搜索范围。多份文件的字段组合默认须落在同一 LogicalDocument；用户可显式切换“同一批次任意文件”，结果逐条件标出命中文件。结果显示命中的文件、逻辑单据、角色、来源及所在批次。

摘要按 Case、原件版本、逻辑单据、**每次 Run × 每份参与源文件**、Run 和 Export Snapshot 分范围保存。逐次逐文件摘要记录任务目标、目标语言、状态、关键字段概况、疑点数、处理人和时间，并引用原件／解析／业务／译文版本及原文证据。摘要属于检索与 `@ `候选排序的辅助层，变更时只重建受影响版本或标记过期；历史快照摘要保持冻结。`@ `可选单票、处理批次、原件或成功导出快照；发送消息时冻结相应 ID 和版本，再按权限查询字段与原文回答，不能直接把摘要当事实。

首版先按用户／团队权限过滤，再用数据库元数据索引和全文检索覆盖上述组合条件与模糊文件名，不为常用字段检索先引入向量库。摘要只随搜索结果返回短文本；选中 `@ `后才加载该票／批次的最小必要业务记忆。点击批次下的原件、疑点或译本复用同一校验工作台与版本深链，历史 Export Snapshot 只读；关闭工作台恢复管理台的筛选、排序和滚动位置。语义 RAG 可在样本证明必要时后加，仍须先鉴权和限定版本。

## 11. Skill 与 MCP 扩展区

这一页保持轻量：列表展示内置／我的 Skill 和 MCP 接入配置，提供创建、编辑、启停、删除、连接测试与最近调用状态，不做复杂市场或开发平台。用户可自行创建 Skill 配置，填写名称、用途、使用条件、版本化说明、参数 schema 和允许的业务动作；导入文本说明后先校验，再由用户启用。内置“单据任务路由”由项目维护，不允许普通用户改写系统策略或跳过业务校验。

用户也可自行新增 MCP **接入配置**，填写已有 MCP 服务的地址、支持的传输方式、认证信息和允许暴露的工具，测试连接、读取工具清单并选择启用。这里的“创建 MCP”指在产品里创建连接与授权记录；在产品里编写、运行和托管任意 MCP 服务代码属于后续能力。首版建议只支持一种经过测试的连接方式和只读调用，写入／外发工具另行评估权限与确认。`/ `选择器与管理区读取同一注册表，只展示当前用户有权使用且实际可连接的能力。

**实现上的关键区分：** Skill 的说明与步骤可作为低优先级、受控的任务提示提供给外层模型；MCP 必须由真实客户端连接、发现工具、校验参数并执行调用，不能靠把名称塞进 Prompt 伪装成工具。用户创建的说明、远端返回内容和文件正文均是不可信输入，不得覆盖系统策略或取得超出票据授权的资料。全局模型密钥等配置放在 `.env`；用户自己的 MCP 凭据只存服务端受控密钥存储，不出现在浏览器、聊天、摘要、日志或提交记录中。扩展失败应显示真实连接／调用状态，核心翻译工作流不依赖任意用户扩展才能运行。

## 12. 可实现的服务与数据组织

首版无需搭建通用多 Agent 平台。按职责组织为：前端对话/管理/复核界面、LangGraph 受限对话图、版本化单证处理图、业务数据库、文件存储、后台任务执行器与事件通道，以及可替换的 OCR/抽取/翻译适配层。对话图只握有受控业务工具，不能替代单证图处理原件；单证图编排有限节点，每阶段产物与版本由业务数据库持久化。首版必须支持字段修订后按依赖失效和重算；[工程技术方案](../技术方案/物流单证智能体_工程技术方案.md)确定以 LangGraph 编排、PostgreSQL 业务状态与独立后台执行协作。长时间人工复核由 Run 状态承接，修改后开启同一 Run 的新执行批次；图检查点不能代替任务队列、对象存储、业务幂等和审核门禁。

| 实体 | 必要内容 |
| --- | --- |
| `Case` | 所属用户/团队、业务名称、状态、创建时间；起运地、原产国、目的地等按各自字段角色与来源版本索引，不合并成一个“来源地”真值；目标语言从 Run 派生 |
| `UploadSession` | 所属草稿 Case、逐文件上传状态、传输字节数、错误类型、上传事件序号 |
| `SourceDocument` / `DocumentVersion` | 原件路径或对象键、文件哈希、文件格式、页数、单票、版本、上传人 |
| `LogicalDocument` / `DocumentSection` | 逻辑单据所属原件版本与 `parse_artifact_id`、`logical_document_id`、类型与人工确认状态；其区段的 `section_id`、页／区域范围和顺序；混合 PDF 可有多个逻辑单据 |
| `ParseArtifact` | 不可覆盖的 `parse_artifact_id`、所属原件版本、引擎与配置版本、原始响应、逻辑单据边界、块/表/行结构、Markdown 副本、来源锚点；源片段绑定本解析版本内的逻辑单据与区段 ID |
| `FieldAssertion` / `Issue` | 所属解析版本与逻辑单据、原值、规范值、人工采用值及依据、单位、来源、审核状态；规则版本、差异、严重度、处置记录；跨节疑点保存所有涉及节 ID |
| `LineItem` / `LineMatch` | 在原件及解析版本内稳定的行 ID、所属逻辑单据、原文锚点与行内字段；跨单据多对多关联、匹配依据、确认状态 |
| `Translation` / `OutputDraft` | 所属 Run、目标语言、逻辑单据与区段 ID、源片段 ID、业务与译文 Revision、译文片段 ID、术语版本、模板版本、预览版本及过期标记 |
| `Run` / `RunEvent` | Case、任务类型、参与的源文件版本与 Task Spec、任务发起人、开始／完成时间、阶段状态、幂等键、外部任务 ID、事件序号、耗时和错误类型 |
| `CaseSummary` / `RunDocumentSummary` / `SearchIndex` | Case 概览及每次 Run × 每份源文件／逻辑单据的短摘要、引用的业务／译文版本、生成时间和过期状态；按 owner/权限、日期、地点字段角色、收件人角色、处理人及文件名建立结构化检索入口 |
| `ExportSnapshot` / `ExportArtifact` | 冻结的 Case 业务版本、Run 与目标语言、各源文件使用的原件／解析／译文版本、复核人／导出确认人、整组校验结果与导出时间；逐源文件版本映射到目标语言译本文件，另挂所选逐源识别稿 PDF，各文件有哈希 |
| `Conversation` / `Extension` | 消息与引用的单票/文件 ID；技能/MCP 配置、权限和调用记录 |

工程基线已选择 PostgreSQL 与 S3 兼容对象存储，本地演示使用 MinIO。单用户演示也必须给所有数据标明 owner，服务端按 owner 授权，不能因为尚无多人界面就省略隔离。原件与大解析结果不进入工作流状态记录。每个收费 API 调用需记录业务 ID、输入版本、步骤、配置版本和供应商请求键／任务 ID；超时恢复优先按供应商支持的键查询，提交结果无法确认时暂停自动重试并进入人工核查。首版任务和界面依同一持久化状态在页面刷新、断网和服务进程重启后重建；可确认的未完成步骤由恢复扫描器继续，不能安全确认的外部任务保持可追溯的待核查状态。

文件与字段访问按用户/团队权限过滤，`@` 和全文/向量检索同样执行权限检查。在隐私文档说明是否使用第三方 OCR/翻译服务，上传界面不设额外告知确认或服务节点列表，演示优先使用获授权、脱敏或合成样本。日志不打印原文大段内容或密钥；删除单票时应有明确原件、索引、预览和导出快照的清理规则。制度和保留期要在部署前确定，而不是由模型自行决定。

## 14. 首版验收场景与可测指标

验收用一票包含图片箱单、PDF 发票、DOCX 补充资料的材料包，同时准备一组正常样本和一组有标注问题的样本。它们既验证界面，也验证事实链；演示样本与调试样本分开。

1. **两种发起方式一致：** 点击主卡片与直接上传文件，均先产生可追踪的草稿 Case/Upload Session，至少一份文件上传成功且任务模式必需条件明确后才由路由 Skill 建立 Run；翻译必须明确目标语言，标准双语交付可作为明示默认。多文件可正确归票，部分上传失败有逐文件原因且不阻断成功文件。
2. **外层边界成立：** 任务处理日志可证明解析、抽取、校验、翻译在单证工作流执行；对话问状态时读取持久化事件，不让对话模型自行处理原始附件。只上传文件并询问 `Consignee` 时，启动不需要目标语言的只读识别/索引 Run，随后引用已解析字段回答。
3. **真实进度可恢复：** 上传/解析/校验/等待复核/导出事件按序出现；刷新或重连不丢任务，不重复显示事件；未测得的阶段不显示虚假百分比。
4. **来源与差异可信：** 高价值字段可回到原页/表格；同一混合 PDF 中的发票与箱单拥有不同逻辑单据 ID 和区段 ID，字段、规则、来源和侧栏筛选不串节，但仍按该源 PDF 交付一组译本。刻意设置的数量或重量冲突必须进入待复核，正常的角色或毛净重差异不能一律误报；无法定位时直说。DOCX 补充材料默认作为其他佐证材料，不被悄悄计入发票/箱单/提单规则。
5. **人工修改有连锁更新：** 修正一个数量并说明原因后产生新版本；受影响的算术、跨单据规则、译文/预览和摘要按依赖更新，旧结论标过期，原件不变；首版可重算整票规则，但不重复运行未受影响的 OCR。
6. **翻译与导出可用：** 数字、币种、箱号等受保护字段在译前译后保持一致；三份输入各生成可点击且可回指源版本的目标语言译本，另生成所选逐源识别稿 PDF；整组 DOCX/PDF 回检字段/表格/文本层和版面，任一必需产物失败则不登记成功导出快照。
7. **历史可找回并可问：** 默认列表按已导出的翻译 Run 展示，一次多文件仍为一行；按日期、来源地口径、收件人角色、处理人角色、文件名与类型可定位批次，点击源文件打开准确版本的校验区，历史快照只读且返回后筛选位置不丢。每次 Run 的每张单据都有可追溯短摘要；`@ `命中摘要后仍回查字段与原文，不越权或把旧版值当最新版。同一源文件存在两个目标语言的译本且当前会话无目标语言时，询问译文必须让用户选择。
8. **扩展入口可用：** 用户可创建并启用一个受控 Skill，`/ `能调用它和内置路由；用户可按受支持模板新建已有 MCP 服务的接入配置，完成连接测试、工具发现和一个已授权只读调用。连接、参数或权限检查未通过时不可用，调用失败有明确状态。

后续用约 30—50 票、多份材料做初步业务评估，分别统计关键字段正确率、明细行完整率、真实错误检出率、正常差异误报率、人工复核时间、可用导出率、每票完整成本，以及单证问答的来源支持率。任何数值目标都应先用样本基线定标，不把竞品宣传数字或模型自报置信度当作验收标准。固定测试集中的刻意植入问题不得漏检，但这不等于对未来所有材料保证 100% 正确。

## 15. 需要在开工前锁定的产品决策

| 决策 | 建议默认值 | 为什么要锁定 |
| --- | --- | --- |
| 目标客户与线路 | 中国中小跨境货代；通用识别／翻译不限线路。线路专属规则先以中国出口至欧盟的一般非危险消费品作验收样本 | 决定首个有限规则包的适用边界，不把其他单据类型挡在通用处理之外 |
| 首版材料 | 发票、装箱单、提单及其他佐证材料；图片/PDF/DOCX | 决定解析样本、字段规则与复核模板 |
| 输出边界 | 首版逐源文件目标语言译本可选 DOCX／PDF，另可选逐源识别稿 PDF；模板发票/箱单后续扩展 | 避免误承诺任意原版式或正式提单重签 |
| 目标语言 | 中文、英文；其他语言由样本决定 | 决定 OCR 与翻译链路的真实交集 |
| OCR 主引擎 | 首接 MinerU 精准解析；用同样本验证定位、表格与费用，不满足门槛时再比较替代适配器 | 厂商文档不能证明字段定位和短物流票据准确率 |
| 有限规则包 | 首批只对中国出口至欧盟的一般非危险消费品启用经审核的少数权威规则；跨类型通用一致性检查独立运行 | 为缺证/HS 风险提示提供可审计依据，其他范围明确显示未覆盖／无法判断 |
| 首版部署 | 桌面优先 Web、单用户演示；首版具备 owner 隔离，多用户协作界面后续扩展 | 控制前端和存储复杂度，同时确保跨用户数据隔离 |
| 复核放行规则 | 高风险事实冲突必须人工裁定；无法判断不能写成通过 | 保持导出文件和审核状态可信 |

以上已确定首接协议和规则包的首批样本范围，但不代表 MinerU、模型或具体法规规则已经通过样本验证。实施时须将权威规则来源、审核记录、模板、解析效果与验收阈值写入对应技术方案及评测文档后，才能把相关专项检查标为可用；未覆盖的线路和货类仍可走通用识别与翻译。
