# 同票多单证交叉核对与格式适配：专项工程方案

版本：v1.0｜日期：2026-10-13｜状态：方案已进入实施；交付与验收状态以第17节和专项台账为准。

目标：把“一票多份材料的识别与翻译”完善为“同一批货物、多主体、多运输阶段的单证关联、交叉核对与人工处置”，覆盖 PDF／图片／DOCX，并以一个明确版本的 EDI 报文作为后续结构化接入样板；在有正式审核依据的范围内提示证书缺失与 HS 编码风险。

本方案沿用现有 React／FastAPI／LangGraph／Celery＋Redis／PostgreSQL／S3 架构。不引入微服务、图数据库、独立向量数据库或多个自主运行的 Agent。本文的新工作流、表、接口、提示词和页面组件均为拟新增内容；原接口继续以[前后端接口与状态契约](前后端接口与状态契约.md)为准，进入开发前应把确认后的增量契约回写该文档并生成 TypeScript 类型。

上位依据：[产品需求总览](../需求设计/物流单证智能识别与转换智能体_产品形态与需求规格.md)、[翻译校验工作台需求](../需求设计/单证翻译校验工作台与工作流_产品设计.md)、[对话 Agent 需求](../需求设计/对话工作台与对话Agent_产品设计.md)、[单据管理台需求](../需求设计/单据管理台_产品设计.md)、[工程架构](物流单证智能体_工程技术方案.md)。类型与货类来源沿用[官方标准调研](../调研分析/物流单据类型与货物领域_官方标准调研.md)，本文不新增未经核验的法规结论。

## 1. 核查结果与本轮补强范围

### 1.1 当前能力与缺口

以下结论来自 2026-10-13 的代码阅读，不是一次新的端到端业务验收。

| 模块 | 当前真实实现 | 本方案需要补齐 |
| --- | --- | --- |
| 单票与上传 | `Case → SourceDocument → DocumentVersion`；补件与替换分开；Run 冻结参与版本 | 有版本的当前材料集合、货物批次与运输阶段声明，避免“同票即所有字段相等” |
| 解析 | PDF／PNG／JPEG／DOCX；原生解析与 MinerU；来源片段、页码和部分结构坐标 | 多版式样本适配、多语表单类型判断、重复页和附件关系；EDI 专用适配器 |
| 字段 | `type_catalog.py`、`field_schema()` 按精细单证 code 和货类配置字段；角色分开 | 类型能力评级、多语标签、稳定货物编号／规格／批号的行级提取、遗漏检测 |
| 关联 | 有 `LineMatchEdge` 和人工主体映射、包装表口径声明 | 同文件／同单证／同批货物／上下游阶段的自动候选、可解释确认；完整一对多／多对一 |
| 交叉规则 | 同运输参考的部分字段比较；明确人工一对一明细数值比较 | 跨语等价、阶段适用性、包装层级和完整范围判定、分批汇总、明确差异矩阵 |
| 疑点 | `RuleCheck`、`Issue`、`IssueDisposition`；五个统一处置入口 | 关联不明与原件冲突分开；比较批次固定；只影响当前适用版本的待办和门禁 |
| 合规 | HS 形式／来源一致性候选，审核发布机制；两个试行材料包 | 正式审核过的小规则包、所需证书和本货批覆盖关系、有效期管理 |
| 对话与管理台 | `@ `冻结授权范围，带来源问答，任务／文件摘要和版本视图 | 消费同票关系及差异摘要、跳转同票对比、补件后的新核对批次入口 |

需要注意的现有实现限制：类型判断主要依赖中英文标题；通用角色映射比较仍主要按词面值；结构化明细列尚未覆盖所有货物标识；现有跨单数量规则明确要求人工确认一对一；仅新增类型菜单不能解决这些限制。

现有鲜苹果证书试行包为 `cn-eu-fresh-fruit-certificate@2026-07-06.1`，代码标记 `legal_review_status=pending`，复核窗口在 2026-10-15 到期。实施时必须重新核对官方文本、审核并发布新版本，不能把项目复核窗口当法律生效时间，不能直接延长旧包日期。

### 1.2 完成定义

一次完整验收应能展示：用户上传同一批货物的发票、箱单和运输／报关材料；系统区分单据用途、建立有依据的关系、提取不同类型所需字段；自动识别真正可比较的差异；用户在两侧原文准确定位并处置；补件后有新核对结果；纯目标语言译本正常导出；历史结果可回溯。

不把“类型识别成功”“模型认为一致”“页面显示通过”单独当作验收完成。

### 1.3 交付优先级

| 级别 | 范围 | 完成条件 |
| --- | --- | --- |
| P0 | 发票、箱单、海运提单、报关单；同票关联；一对一及有完整依据的拆分汇总；对比矩阵与原文定位 | 不依赖 mock，完成正常、异常、正常阶段差异和补件闭环 |
| P1 | 快递／空运／公路运输；更多版式；同一单证的语言版本；受审核小合规包 | 每类有真实结构样本和字段、规则、定位验收；规则来源与范围可查看 |
| P2 | 一个 UN/EDIFACT IFTMIN 报文版本；更多国家、行业和单证 | 报文版本锁定、结构回检与跨格式对比通过；每个新法规包独立审核 |

类型目录可以继续覆盖粮食、果蔬、金属、矿物、能源、危险品、受控物项和货币运输等领域；首轮不宣称所有类型和监管规则均达到同等成熟度。

## 2. 业务定义与不可破坏的约束

### 2.1 六个对象各自负责什么

| 对象 | 定义 | 不能混同的对象 |
| --- | --- | --- |
| Case | 一票业务档案，绑定一批业务货物，容纳其单证及运输过程 | 不是一次上传、一个文件或一个翻译任务 |
| Cargo item | 货批中的商品／规格／批次明细，以稳定内部 ID 引用 | 不用不同单证中的行号作为同货依据 |
| Shipment leg | 一段运输／交接，含方式、起终点、承运主体和时间 | 装货港、目的港、承运人接货地、最终交货地不是同一个字段 |
| Logical document | 一份有独立用途的单证；一个 PDF 可含多份逻辑单证 | 一页／一个物理文件不一定是一份业务单据 |
| Document relation | 原件、修订、译本、附件、主分单及上下游引用关系 | 相同货物不代表相同单证；同编号也不必然同一版本 |
| Comparison batch | 在冻结材料、字段版和关联决定上执行一次核对 | 不读取不断变化的“当前全部文件”作为运行中隐式输入 |

Case 允许运输拆分、换装、多个交接主体及多张运单。若同一合同包含多个无关货批，必须由用户分票或显式关联到独立货批；不得因订单号一致自动合成一个货物身份。

### 2.2 强约束

1. 原件与机器候选不可覆盖，人工采用值和关联决定形成新版本。原件冲突不会因修改译文而消失。
2. 卖方≠发货人，买方≠实际收货人，通知方≠收货人，货代≠承运人。只有明确映射依据才能比较为同主体。
3. “中间人”必须具体到角色及阶段；未知时保留“未明确角色”，不得强行归入收货人。
4. 起运地、原产国、卖方地址、接货地、装卸港及最终目的地分别保存。
5. 同一原件的系统译文不得作为第二份独立业务证据，回传的本系统导出件通过快照引用识别；去重证据不足则只是候选。
6. 数值比较须同货、同范围、同计量含义、可换算单位；毛重不和净重、实重不和计费重直接比较。
7. 只有当前核对版本中有充分证据、影响关键交付的未解决红项阻断疑点门禁；黄项和无法判断不硬阻断。技术完整性、权限和版本门禁保留。
8. 五个疑点操作固定为：修订译文／忽略并记录／Agent 处理／应用推荐修改／补充上传。忽略理由选填。
9. 一 Run 一目标语言；导出纯目标语言译本，可选识别稿 PDF，不导出复核报告。独立核对工作流不生成译本。
10. 用户记忆、会话记忆、单票事实分别隔离；新会话只加载用户确认记忆、当前上传、显式 `@ `范围和本会话上下文，不加载其他会话。
11. 沿用30天留存及用户申请整票删除；新关系、批次、索引、对象和检查点必须纳入同票撤权与清理链。查询与普通问答不刷新期限。

### 2.3 一票多单证的完整业务例子

一批同SKU、同批号货物共100箱，卖方A售给买方B，实际收货人C，货代D安排两段运输。用户上传英文发票100箱、中文总箱单100箱、第一分单60箱、第二分单40箱及一份本系统生成的法语发票译本。

1. 发票与总箱单是不同用途的原件；法语译本只关联英文发票，不额外计入货物或作为原件一致性证据。
2. A、B、C、D按角色分别展示；买方B与收货人C不同并不产生主体冲突。两段路线分别保存，不能要求全部地点或承运人相同。
3. 有完整分批引用和相同包装层级时，建立100对60＋40的匹配组。发票／总箱单按整批比较，两张分单按覆盖组合比较；总箱单与分单不能再重复求和为200箱。
4. 仅收到60箱分单且第二分批材料未提供时，显示“当前材料只覆盖60箱”，不给“货物少40箱”的确定性结论。第二分单为38箱且用户明确两份已覆盖完整范围时，才可得到“应覆盖100箱，现有完整分单合计98箱，差2箱”的冲突。
5. 用户补传正确分单后，旧100对98结果仍可回看，新scope经重核对形成新批次；译文范围要纳入新件则新建翻译Run。旧成功导出始终保持原样。

这个例子同时作为X0样本、X3规则和X4页面联调的贯穿案例，避免各模块自行定义“同票”和“完整”。

## 3. 数据模型：在现有事实链上增加关系与冻结范围

### 3.1 原有对象复用

继续使用 `Case`、`DocumentVersion`、`ParseArtifact`、`LogicalDocument`、`SourceSegment`、`SourceAnchor`、`FieldAssertion`、`LineItem`、`BusinessRevision`、`RuleCheck`、`Issue`、`IssueDisposition`、`Run`、Outbox 与 ExportSnapshot。

字段保持原件转写、候选、规范值、人工采用值四层。规范化只用于比较与显示，不修改原件；事实值与角色、范围、出处必须一起传递。跨单证核对结果引用上述 ID，不复制一套无来源“主单票数据”。

### 3.2 六组拟新增表

| 表 | 核心内容 | 不变量 |
| --- | --- | --- |
| `case_scope_revisions` | `case_id`、递增 revision_no、父版、当前参与 `document_id/version`、替换／附件／排除声明、货物／主体／阶段声明、证据引用、操作者和时间 | 每版追加不可变；JSONB 使用版本化 Pydantic schema 校验，不接受任意键 |
| `relation_assertions` | 关系种类、两端逻辑对象及版、来源依据、判定方式、候选／自动已证实／人工已确认／拒绝状态、supersedes | 每条不可变，确认／拒绝追加新记录；自动判定理由可回放 |
| `cargo_match_groups` | 比较关系、一对一／一对多／多对一、共同货物标识、范围、包装层级、汇总方式、完整性、依据、替代关系 | 明确左／右集合及唯一成员，不把多个独立边直接相加 |
| `cargo_match_members` | group_id、左／右、LineItem ID、取值依据、可证明的分配数量（如有） | 同组同侧不重复；同一比较中不能重复计入同一实物流量 |
| `comparison_batches` | 所属 Run、状态、父批次、材料清单、字段业务版、scope版、采用关联／匹配ID、规则及提示词版本、输入哈希、输出摘要 | 运行输入不可变；完成结果追加写；旧批次不随当前文件变化 |
| `run_comparison_bindings` | 翻译Run→已完成比较批次、交付范围及依赖哈希、建立／替代记录 | 记录追加不可变；Run的当前绑定指针唯一；只有经证实同依赖、同规则的完成批次可复用 |

上述是六组关系表，其中匹配成员独立于匹配组。初版货物、主体、运输阶段是 `case_scope_revisions` 中的强类型结构，使用稳定内部 ID 和来源引用；不存整篇原文。需要高频按节点搜索时，再依据实测将相关投影拆为关系表，初版不提前建立图数据库。

scope 中的主体／阶段声明属于业务确认，并不证明原件确实包含该事实。比较结果必须说明依据是原件、人工声明还是模型候选；证书法律适用的决定仍须满足规则包要求的前提。

Case增量保存 `current_scope_revision_id`、`current_comparison_batch_id`，翻译Run增量保存 `current_comparison_binding_id`；这些是可更新的投影指针，不修改指向的历史记录。scope指针按用户决定更新；比较指针仅在结果发布事务中按预期依赖更新，不按返回时间取“最新”。

### 3.3 扩充行级字段而非只加页面名称

`LineItem` 需增量支持：SKU／客户商品码、规格型号、货批／lot、原件项号、包装标识／箱号范围、原产国，以及原件存在的净重单位、毛重单位和计费重量。HS 保持字符串。一个表有两个数量口径时，扩展强类型 `measurements`，每项含 quantity_kind、value、unit、原件列／来源 ID；不得覆写到同一个 quantity。

公共 scalar 列保留兼容；新增列和 measurements 只表达原件有值的内容。对所有新字段明确“未出现／未识别／未确认”，不能因 schema 列出字段就造出空白红项。

### 3.4 版本链与并发

材料替换、类型／事实修订、关系确认是三类变更：前者更新 scope版，事实修订更新 BusinessRevision，关系确认追加 relation／match 决定并更新 scope版；纯译文编辑只更新 TranslationRevision。只有影响冻结比较依赖的变更才使比较绑定过期；纯译文编辑使译文QA／预览／确认失效，不使无译文依赖的原件比较过期。旧批次仍能只读打开。

写入命令校验 `expected_case_version`、scope ID、业务版 ID及 `expected_review_state_version`；在同票短事务锁内追加决定、更新当前指针、写审计及 Outbox。重复请求用 Idempotency-Key 复播结果；并发冲突返回409，保留用户输入并提供当前版本，不能“最后写入覆盖”。

冻结清单至少包含：文件版本及哈希、解析ID／配置哈希、逻辑单据与字段业务版、原件／采用值比较基准、scope与关系决定、匹配组、规则及字典版本、提示词哈希、任务明确交付范围。可派生内容用规范JSON计算 SHA-256；用户可见排序不改变输入哈希。

### 3.5 原件与人工采用值双轨核对

默认矩阵展示当前采用值，同时可切换原件候选。每条结果区分 `basis=source` 和 `basis=adopted`；冲突原值和处理记录永久保留至整票清理。字段纠正后可得到“采用值已一致、原件存在差异”；不得展示为“原件从来没有冲突”。

### 3.6 检查、疑点与跨Run绑定的归属

在现有 `RuleCheck` 上增量增加可空 `comparison_batch_id`、`comparison_basis`、`stable_check_key`；在 `Issue` 上增加同批次引用与稳定问题键。旧检查／译文QA的batch引用保持为空。跨单证Issue必须引用同批次的RuleCheck；生产Run、Case、租户、BusinessRevision与batch一致，由组合外键及写入验证约束。batch固定一个Case级BusinessRevision；其实际字段断言／行集合另在冻结清单逐项列明，不把不同版字段混用。

新增唯一约束为“tenant＋batch＋规则版本＋稳定检查键＋comparison_basis”；同批次同检查同问题键只建一个Issue。来源、规则输入与结果内容不可覆写；人工处置继续追加 `IssueDisposition`。计算中间结果不提前开放；结果集以batch完成发布为可读边界。

batch生产Run可以是consignment_check，也可以是translate_review@2：翻译内首次核对子流程直接把batch归属本翻译Run，不额外派生核对Run；补件／关联重算则遵循§11.1建立独立核对Run。翻译Run始终通过binding消费batch，包括引用自己生产的batch，统一查询路径。

跨Run复用不复制RuleCheck或Issue。处置提交原Issue ID，服务端验证当前票／批次和版本；同一个原件问题的有效处置可被多个经授权且依赖相同的翻译Run消费。译文问题仍归各自目标语言Run，禁止跨语言继承译段处置。

统一复核查询必须合并“本翻译Run当前业务／译文版的本地QA”与“当前有效binding指向batch的跨单证Issue”，去重后按交付范围计算。现有按 `Issue.run_id == translation_run.id` 查询的路径必须改造；不能仅注册新API而继续漏读其他生产Run的红项。复用原处置API时一并扩展batch授权和前置版本校验，不新建第二套处置记录。

### 3.7 补件后的完整业务版装配

现有抽取Worker会按本Run断言集合建立业务版，不能直接假定它已包含整个Case所有当前材料。新核对执行器先冻结scope和起始业务版，解析完成后为该scope装配完整有效字段视图：复用仍有效且已有明确采用决定的断言，仅替换被指定新件／新解析替代的部分，加入新增材料断言，并排除scope明确移出的旧件。

采用值与机器候选同时出现时按原有业务采用规则选取，不能因新一轮模型结果覆盖人工确认。装配结果追加一个BusinessRevision，记录父版、全部参与字段ID及每个文件的解析映射；batch最终冻结这个已解析业务版，Task Spec仍保存启动基线。明细采用值及映射在冻结清单列明，不依赖可变的行缓存。

装配及当前指针更新需Case锁和输入版本校验；同票并发新scope已发布时，旧作业仅保留自己的完整视图，不回退Case当前版。若翻译Run要消费该新业务版，先按其固定文件／选区重新验证范围并运行受影响译文QA，不能仅替换business_revision_id使旧预览假装兼容。

## 4. 单证与格式适配

### 4.1 处理配置的最小结构

在现有目录上注册版本化 DocumentProfile：类型code、基础类型、常见多语标题与标签、主体角色、头字段与行字段、逻辑区段／附件特征、版式解析策略、业务建议字段、规则适用条件、样本版本和已验证能力。

能力状态分为“目录支持”“字段已验证”“跨单核对已验证”“正式规则已审核”。前端选择器可以全部提供，但不得把目录状态说成该类型所有格式均已适配。

字段要求分三种：原件标签出现但抽取遗漏；用户业务清单要求；经过审核规则适用后要求。三者来源和严重度不同，不能一律称“法定必填”。

### 4.2 类型与主要核对逻辑

| 类型 | 角色与头字段 | 行／结构字段 | 主要检查 |
| --- | --- | --- | --- |
| 商业发票 | seller、buyer、编号、日期、币种、贸易术语、订单／合同引用 | SKU、品名、规格、批号、数量／单位、单价、行金额、货值及运保费 | 费用口径清楚才核合计；与箱单按货物标识匹配 |
| 装箱单 | shipper、consignee、箱单号、发票引用、唛头 | 箱／托／件层级、包装范围、数量、毛净重／单位、体积 | 跨页行和小计不重复；完整同层汇总；与货物行对应 |
| 海运提单 | shipper、consignee、notify_party、carrier、货代、主／分单号 | 接货地、装卸港、交货地、船／航次、柜／封号、声明件重、装船日期 | To order保留；主分单、港口及阶段关系；集装箱货不等于单一Case |
| 报关单 | 境内收发货人、境外主体、申报主体、编号、监管方式、日期 | 项号、货描、规格、HS、原产国、成交及法定数量／单位、价格币种 | 各数量口径独立；申报值与发票值先检查费用／计价依据；不自动最终归类 |
| 快递单 | 寄件人、收件人、承运人、地址电话、追踪／运单号 | 件数、实重／计费重、服务信息、报关附页 | 地址角色；运单与CN22/CN23等附页分开；条码只接受真实解码 |
| 空运单 | 主单／分单、shipper、consignee、carrier、货代 | 始末机场、航班、件数、实重、计费重、尺寸 | 主分单、同航段匹配；不能把计费重差异报成货物重量矛盾 |
| 公路／铁路运单 | 发收及承运方、运单号、车辆／车皮、始末地点 | 交接日期、货物、包装、保留意见、签收数量 | 分段承运主体可不同；实际签收差异要结合保留意见 |
| 证书／许可证 | 签发机关、证号、签发／有效日期、引用原件、货物主体 | 覆盖货类／货批／数量、声明、附页 | 文件是否提供、与本货批关系、适用日期；不是真实性鉴定 |
| 通用佐证 | 原件明确角色、引用号、日期、主题 | 原文可辨内容和实际结构 | 支持读取翻译；类型或用途不明时给候选，不强套必填规则 |

货类Profile叠加关注字段，例如果蔬的学名／批号、金属的牌号／成分、石油天然气的计量基准／温压、危险品的UN号／正确运输名、受控物项的最终用途／许可引用、现钞的货币种类／面额。货类只指导提取和有依据的规则，不凭一个关键词推断危险品或监管义务。

### 4.3 解析选择与结构保护

| 输入 | 解析路径 | 关键边界 |
| --- | --- | --- |
| 原生PDF | 文本／表格提取；仅异常页或区域进入OCR | 重复文本层、扫描叠层及跨页表格要去重；文字多不代表完整 |
| 扫描PDF／图片 | MinerU解析及布局；关键低清区域受控视觉复读 | 复读保留候选和来源，不静默补全编号／主体；无坐标只说明可定位精度 |
| DOCX | 正文、表格、合并格、分页与受控图片处理 | 文本框／脚注／图片未覆盖需明确提示；不执行宏或外链 |
| EDI | 专用语法适配→业务段／限定符→字段与来源模型 | 不能交给OCR；消息类型、目录版本、转义、段计数、限定符必须验证 |

类型识别采用“标题／布局确定候选→不明确时结构化模型判断→必要人工确认”；模型输出typecode和证据，不改已有明确的人工确认。增加法／西／俄文标签，避免五语界面支持却只认识英文表单标题。

表格结构中保留原件行列、合并格、重复表头、小计、总计和续页关系。重复表头不作为货物行；序号只能用于定位。同页多份单证须切逻辑单据，附件需保留明确引用；不能凭空按每页拆开。

### 4.4 翻译预览与格式适配共同验收

继续采用结构骨架＋对应译段：左侧展示识别后的原件，右侧默认仅目标语言译文，可切双语阅读；最终译本不加入“原文／译文”标签或复核报告。原件表格、横线、合并格及分页边界保留，译文变长时允许单元格扩展、合理换行和适度调小字体，禁止截断内容或把不同货物行并成一行。

分页以原件结构为对应基础；译文溢出时显式延续该页内容、保留原页映射，不为了页数相同压到不可读。没有可靠布局时使用结构还原稿并显示实际还原状态，不能宣称像素级复刻。预览与导出使用同一渲染配置、相同译段及结构版本，避免页面看着完整而导出缺行。

每种宣称“字段已验证”的格式同步核验跨页提取、来源跳转及译文结构；只通过文本抽取的样本不能升级为格式适配完成。Source PDF是识别稿渲染输出，明确与上传原件PDF的区别；原件仍可按现有文件读取能力下载。

## 5. 自动关联与货物匹配

### 5.1 先关系后比较

关系类型至少包括：完全相同文件、同单证修订、同单证语言版本、附件、显式业务引用、主单／分单、同货、上下游运输段。每种关系有单独判据，不合并成一个“相似度”。

候选检索只在当前授权Case的冻结材料中进行，优先订单／运输引用、批号、SKU、柜封号及明确源文交叉引用。装货日期、相同公司、相同港口只是辅助特征；柜号可能含多票货，订单号可能含多批货，均不能单独自动证明同货。

### 5.2 自动确认政策

| 级别 | 条件 | 行为 |
| --- | --- | --- |
| 确定性关联 | 哈希一致的同一文件；经授权核验的本系统快照来源；有唯一且无冲突的明确编号引用和范围证据 | 自动建立对应关系，保存规则及来源 |
| 有充分证据的业务匹配 | 明确同货／批次引用，唯一SKU＋规格／批号，包装／阶段口径明确，候选无竞争 | 在对应规则通过样本精度门槛并启用后自动采用；否则保持候选 |
| 语义候选 | 多语货描、缩写主体或缺少稳定编号，模型提出可解释对应 | 让用户确认，不直接产生硬阻断红项 |
| 矛盾／范围不足 | 相同引用对应多货批、多个等价候选、分批范围不明、证据被新版本替代 | 标记待关联／无法判断，给出缺少的依据 |

不使用模型自报0.95置信度作为自动确认门槛。先以规则、唯一性、来源完整性排除风险，再用独立样本校准允许自动化的类别。自动化能力可按类型／客户格式关闭，无须关闭整个识别流程。

### 5.3 主体和地点归一

主体姓名／公司名、地址原值保留。比对值可做空白、大小写、Unicode、可证明的地址缩写规范化；跨语言名字仅形成候选。税号／注册号一致且角色、范围明确可作为强证据，但不同国家号码体系不强比。

地点保留地址、国家／地区、港口／机场代码及各自角色；只有原件提供代码或已验证字典映射才能做确定性等价。代码表需版本及来源。不得因为“Shanghai”和“上海”相似就把所有上海地址视为同一交货地。

### 5.4 明细匹配与分批汇总

一对一优先使用稳定货物标识＋规格＋批号；名称相同但规格不同分开。无唯一编号时模型提出候选，并显示两侧货物描述和推荐理由。

一对多／多对一必须创建匹配组：左集合、右集合、同货依据、比较量类型、单位、包装层级、完整范围、是否含小计以及实际分配依据。只在完整组内计算 `sum(left) 与 sum(right)`；分批不完整只能提示“已提供60／总100，尚缺40的材料或范围说明”，不能说实际丢失40。

多对多首版仅展示候选并允许人工拆成可证明的一对一／汇总组；没有可证明的分配关系不自动汇总。不得对边图求和，避免同一行被重复计数。

## 6. 规则引擎与疑点判定

### 6.1 可执行规则契约

每条规则至少定义：ID及版本、适用类型、左右角色、阶段约束、字段／行量类型、前提、归一化器、比较器、单位／容差、完整性判据、证据要求、严重度条件、不能判断条件及权威／业务依据。

结果分别保存：`status`（passed／failed／undetermined／not_applicable／not_covered／not_run）、`difference_kind`（真冲突／格式等价／正常阶段差异／范围不足）、`severity`（red／yellow／unknown）、证据及计算过程。unknown在界面显示“无法判断”，不显示成通过，也不默认画红色。

输入缺失、解析遗漏、关联不明、规则未覆盖不等于原件冲突；规则状态、疑点待办状态、导出门禁是三层独立数据。

### 6.2 首轮规则清单

| ID主题 | 前提与比较 | 输出 |
| --- | --- | --- |
| document.reference | 明确同一引用对象，比较发票／订单／运单引用 | 有证据的编号矛盾红；OCR可疑黄／无法判断 |
| party.identity | 已证实同主体；名称、税号、地址按字段规则分别核对 | 地址格式等价不报错；关键主体确实不同且应一致才红 |
| transport.location | 同阶段同含义地点，或有上下游交接关系的终点→下一段起点 | 阶段正常差异单列；不同类型地点不比较 |
| transport.container_seal | 同柜、同阶段／同交接范围 | 柜封号差异结合换封记录，缺记录给候选，不能假设永不变化 |
| transport.timeline | 相同事件、可确定日期和时区 | 日期歧义先确认；预计／实际分开，不因时区跨日误报 |
| goods.identity | 同货组内SKU／规格／批号 | 规格／批号冲突说明影响，无法匹配不报数量冲突 |
| goods.quantity | 同货、同量类型、同单位或有明确换算 | 有完整覆盖的数值不符红；分批不全无法判断 |
| goods.packages | 同包装层级，或原件明确装箱关系 | 件／箱／托盘不直接相加；明确转换后可算 |
| goods.weights | 净对净、毛对毛、实重对实重，精度和单位确定 | 明确容差内一致；计费重和实重差异不硬报 |
| invoice.amount | 同币种、明细完整、费用／折扣与计价基准明确 | 以Decimal计算；默认不能跨币种或直接比较报关计价值 |
| hs.source_consistency | 同货，编码有直接来源，版本／国家口径已知 | 国际六位及国家扩展分开；候选差异不直接最终归类 |
| translation.fidelity | 本原件与对应目标译段 | 编号／数值／角色／遗漏／结构问题沿用译文QA，不能伪装成独立单证矛盾 |

数量／件数在精确整数口径下容差0；重量使用规则配置的绝对／相对容差及原件精度，不全局统一“1%”；金额沿用明确币种精度与有依据的舍入策略，不把全部币种默认当两位小数。规则无法确定有效精度时输出无法判断。

### 6.3 用户可读的疑点结构

每项包括：问题是什么、两侧原值与单位、参与单证及阶段、已证实的关系、差异值／比较方法、为什么影响本次交付、推荐动作、来源位置及当前版本。

示例：发票100箱，箱单98箱；已确认同货、同包装层级、完整范围，差2箱。推荐先确认是否另有分批箱单；若OCR写错则对照原件修订；原件确实不同则补充正确材料或由用户判断后忽略。不能只写“数量不一致，请处理”。

### 6.4 五个操作的具体边界

| 操作 | 本轮行为 | 不允许的行为 |
| --- | --- | --- |
| 修订译文 | 对当前译段手动编辑，显示保存后预览；非译文问题解释其作用边界并允许选择相关译段 | 不能把译文改成100来掩盖原件98；无译段不产生假保存成功 |
| 忽略并记录 | 原问题保留，当前待办关闭，理由选填，记录操作者／时间／版本 | 不能更改原规则结果为passed；不能绕过权限或缺失产物 |
| Agent处理 | 用户意见→受控建议→展示修改前后和依据→确认应用；普通译文可沿用已授权编辑范围 | 不自动变更原件事实、主体关系或HS；这些需要明确确认 |
| 应用推荐修改 | 推荐必须有明确对象、旧值、新值、依据及影响范围；安全的确定性修改可直接应用 | 对证据缺失只引导补件／确认，不能捏造数值；不能把“建议核对”当可自动改值 |
| 补充上传 | 上传进入同Case；选“新增佐证”或“替换指定原件”；验收成功后生成新scope并标记旧核对过期，用户点击重核对后建立新Run和批次 | 不改旧Run输入，不以新文件覆盖历史对象，不自动认定新件是真实正确版本 |

关联确认在同票对比的“待关联”区完成，属于业务关系声明，不添加第六个疑点按钮。疑点中的Agent处理／推荐修改可引导到该区，返回后恢复疑点位置。

同一疑点可能有多个译段：必须让用户选择文件、目标语言与译段再编辑，不因没有唯一字段就禁用所有处理意见。

### 6.5 疑点重算和去重

采用稳定问题键：规则ID＋比较对象集合＋字段／量类型＋范围＋comparison_basis；输入哈希和规则版本另存。原件和采用值两轨分别存结果，禁止跨basis合并或继承。新批次下同对象同输入、同规则及同basis才可继承明确有效处置，追加带原处置ID的继承记录；新原件、新值、新关系或新规则导致输入变化时，旧处置不能自动放行，新结果显示“条件已变化需重新判断”。采用值通过不自动解决原件冲突。

已解决问题默认不在当前未解决列表；旧原件冲突和忽略仍在历史记录。页头计数、列表、复核完成按钮和导出门禁从同一批次同一状态投影读取，禁止分别计算导致“列表清空但按钮仍阻断”。

## 7. 目的国、证书与HS规则包

### 7.1 三层检查

1. 通用材料：根据用户明确业务清单检查有没有提供，不称为法律义务。
2. 正式规则适用：确认原产／发运／目的地、适用领土、货类与用途、进口日期、运输形态等必要条件；不清楚先澄清，范围外显示未覆盖。
3. 证书覆盖／编码风险：查看证书是否对应本货批、数量、签发日期、附件和声明范围；HS检查依据采用适用税则版本及国家口径。

证书“没有上传”“已提供但读不清”“不属于本批货物”“已提供且覆盖候选”分别展示。材料完整性未声明时，只说“当前材料未见”，不宣称现实缺证。读到印章不证明合法签发或真实性。

### 7.2 发布契约

规则包必须有：不可变版本、官方URL／文件哈希、条款、来源获取及审核日期、法律有效期、项目复核期限、国家／领土、货类及例外、条件表达式、要求的证书类型和字段、审核人／依据、状态（draft／reviewed／published／expired／withdrawn）。

只执行已发布、法律适用及项目复核期限有效的版本。法规更新撤回时新任务不使用；旧快照可回看原依据，但不承诺当前仍适用。紧急发现错误的版本禁止用于新导出，已有历史快照保持原样并附当前失效说明。

规则选择分两层：内置通用核对必跑；法规包只运行已确认适用者，用户选包不等于系统证明适用。先完成一个经复核的窄范围证书包及一组已审核货描／编码候选，不无限制全球检索法规并即时生效。

### 7.3 合规能力验收

同一包须具备适用且当前缺证、适用且证书对应、证书属其他货批、不适用、条件不足、到期／撤回六组样本。每组给出来源、条款与适用原因。只有明确关键缺证且完整材料范围已确认时可产生红项；法规未覆盖／未审定不产生“通过”。

## 8. LangGraph与模型调用安排

### 8.1 注册工作流

保留 `read_index@1`、`translate_review@1` 和所有冻结提示词。拟新增 `consignment_check@1`：输出同票核对批次及复核结果，不生成译文和正式导出。拟新增 `translate_review@2`：在现有翻译任务中复用同票核对子流程；不能直接修改旧版本图。

共享执行链：冻结范围→已有解析复用／新增解析→类型区段→字段与明细提取→来源验证→关系与匹配候选→确定性核对→发布比较批次。翻译版继续执行译段翻译→译文QA／预览→发布复核。

初版只增加“关系匹配”和“比较结果发布”两个明确业务节点，其余细分在领域服务函数中；避免每条规则一个图节点。检查点仅存ID、游标和状态，不存原文或密钥。

关系不明默认只阻止依赖该关系的规则，不停止全部翻译。只有无法继续的类型／解析边界、缺明确目标语言等原任务必要输入沿用 InputRequest等待。待关联决定可在工作台处理，确认后以新批次重算，避免大量反问阻塞普通问答。

### 8.1.1 新工作流状态与发布事务

拟为Run增加仅用于 `consignment_check` 的成功终态 `checked`；与 `indexed`、`exported`分开，不能用事件名称 `completed`冒充现有Run状态。此枚举变更必须在X0进入正式契约，在X2迁移及注册器中落实，前端穷举、状态过滤、allowed_actions、取消／重试判定与后台监控同时更新。

| 执行情况 | 核对Run状态 | batch状态／读行为 |
| --- | --- | --- |
| 任务受理／执行 | queued／processing | queued／processing；只能读真实进度，不能当作无疑点 |
| 缺运行必需输入 | awaiting_input | awaiting_input；沿用InputRequest；恢复用同Run新Epoch |
| 仅部分关系不明，其他规则可运行 | processing→checked | completed；相关行undetermined，待关联计数大于0；不等待用户才发布 |
| 核对执行完，包括发现真实冲突 | checked | completed；checked表示计算已完成，不表示业务全部通过 |
| 可安全重试／受理不明／最终失败 | failed_retryable／paused_reconcile／failed_final | 对应失败／核查状态；不得发布部分结果为完成 |
| 用户取消 | cancelled | cancelled；旧成功批次只读，晚到不得推进当前指针 |

翻译Run仍沿用awaiting_review→ready_to_export→exporting→exported，所含batch完成不提前把翻译标为完成。独立核对Run不进入导出状态；复核工作台仍允许处置其Issue，顶栏导出按钮依据工作流能力隐藏，纯核对无译段时五个动作保留并准确提示适用范围。

发布前核验租户、Case未删／未到期、Run租约及epoch、冻结输入。短事务内登记完整RuleCheck／Issue及计算结果、batch完成、匹配候选、适用当前指针、Run状态、RunEvent和Outbox；外部调用不在事务内。结果较多时先按batch写不可见准备数据，最后原子切换可读状态。失败回滚或准备数据仍不可见，不产生“已完成”事件。

若旧输入作业晚到而Case已有新scope，保存其固定输入的历史结果即可，禁止更新Case当前比较指针或其他Run的binding。重复发布由结果唯一键和步骤租约保护，只写一次完成事件。续答扩展为read_index的indexed或consignment_check的checked；冻结实际batch／证据及原问题，每项续答只唤醒一次，继续重验授权和会话状态。翻译完成通知复用原任务卡及事件，不混入只读识别的indexed语义。

### 8.2 同票核对与翻译的范围

核对范围可包含一票当前有效的多个文件，翻译范围可以只是其中用户选择的文件。两者在任务卡明确展示，不默认把全部文件都收费翻译。对话选用已有已完成比较批次时服务端验证全部依赖；不一致则创建新批次。

翻译门禁绑定具体比较批次及交付对象。仅当红项影响本次交付文件／同货范围，或规则明确为该范围的整票义务时才阻断；不相关运输阶段的红项不能无解释阻断所有文件。用户减少交付范围不能绕过仍适用的整票证书要求，范围改变必须重新计算适用性并留痕。

### 8.3 模型职责与统一提示词

| 提示词键（拟新增） | 调用输入 | 输出与权限 |
| --- | --- | --- |
| `document.classify` | 有界标题、结构和必要区域 | 类型候选、边界、证据ID；无权创建已确认事实 |
| `consignment.associate` | 同Case候选主体、引用、阶段、货物片段 | 关系种类、对象ID、支持／反对证据和待确认原因 |
| `consignment.match_goods` | 由确定性检索选出的有限明细候选 | 一对一／汇总候选，规格和范围依据；不能自行填数 |
| `consignment.explain_difference` | 已落库规则结果和来源短摘 | 问题、影响、处理建议；不能更改规则或严重度硬条件 |

沿用 `document.extract`、`document.translate`、语义QA和疑点Skill，在 manifest注册新版本／哈希，旧版本不删除。`consignment-review@1`内部Skill只提供关系、范围及疑点解释准则，不替代数值引擎、不授予原件修改权限；与 `document-issue-review`共用五动作政策，避免两套按钮和处置语义。

所有调用经现有Model Gateway读取.env中的OpenAI兼容角色配置；分类／关联复用extract角色，解释复用chat或extract角色，视觉复读复用vision，不新增供应商耦合。文档文字按不可信材料注入，禁止执行其中“修改规则／导出密钥”等指令；系统、配置、其他用户信息不进入上下文。

### 8.4 性能、并发与重试

先结构化候选检索，再必要模型；同票n个明细不做所有两两模型比较。默认每行最多5个候选、每次匹配批输入不超过已配置预算；可设每票候选总预算，超过后分组分页或转人工，不静默截掉材料。

已有解析／抽取只在文件哈希、解析配置、type/schema及提示词等依赖完全相同时复用。确定性归一化和规则在进程内运行，不付模型费用；模型／OCR耗时作为独立进度显示。

沿用服务级、租户级和Run预算。当前项目租户模型并发默认1，方案不偷偷提高它；发布前基于服务器容量调整。聊天和单证使用现有分队列，避免长OCR阻塞对话。

读调用瞬时网络／429／5xx按网关退避和Retry-After重试，有上限；输入schema、401／403、确定性规则失败不盲目重试。OCR已受理任务先轮询原task_id，不能因超时重新提交收费任务。幂等指纹为冻结输入＋步骤版本；Celery重复投递不能重复模型调用、事件、比较批次或Issue。

取消保留已成功物料和审计，停止新外发；晚到结果先核验取消／删除／版本状态再归档或清理。新批次失败时旧成功批次可只读，但不能充当当前版通过结论。

## 9. 页面联动与交互细则

### 9.1 对话与任务准备

主卡片保留原入口；任务选项增加“核对同票材料”“核对并翻译”。已 `@ `一票时上传先明确“补充到该票／新建一票”，避免误并票；无关联默认新票。选择后任务卡列材料、类型、核对范围和翻译范围，缺语言仅对翻译任务询问。

进度按冻结、解析、提取、关联、核对、翻译、预览各展示一次；下方可折叠查看文件数量和细节，不把每批模型调用塞进聊天。完成卡显示已核对文件数、未解决红黄项、待关联数及“打开同票对比”。普通领域知识问答不进入该工作流。

`/ `内置Skill通过现有注册器路由新工作流；模型仅提出受控Task Spec，服务端重新校验权限、参数、版本与能力。发送“比较这票发票和箱单数量”时，需解析明确Case、文件／范围；无明确对象才澄清，不能隐式搜索用户全部单票。

### 9.2 复核工作台：同票对比标签

在“总览、原文与译文、字段、疑点、处理记录”的现有标签中新增“同票对比”。字段页继续只展示当前逻辑单证字段；差异矩阵独立，不把所有比较疑点灌进字段行。

对比页结构：顶部批次／材料范围与更新时间→可折叠主体和运输阶段概览→差异筛选→比较矩阵→右侧证据栏。顶栏复核完成／导出沿用紧凑固定区域，不重复增加底部操作条。

矩阵第一列固定字段／货物身份，其他列按文件／逻辑单据排列；多文件横向滚动，表头与首列sticky，正文独立纵向滚动。超过4列默认只展示当前比较组，其余用文件选择器切换，不能把侧栏撑到不可读。920px以下切两份单证比较，窄屏上下切换证据，保留选中差异。

默认筛选“未解决差异”；可切全部、正常差异、待关联、历史已处理。红用现有风险色，黄用警告色，无法判断用中性灰；蓝色仅用于选中和证据高亮，不能让选中态看成新增风险。

一行可展开两侧原值、规范值、单位换算及依据；正常阶段差异默认折叠。点击定位不改变当前标签或清空筛选；右侧切对应原件／译段并滚到准确锚点，蓝框高亮约2秒。若坐标不可靠则定位页／结构块并说明精度，禁止画虚假精确框。双侧定位可逐侧切换；每侧有独立滚动容器，避免滚动锁死。

待关联区显示推荐关系、支持与反对证据、“确认关系／不是同一对象／修改对应范围”，操作生成新scope与核对批次；这不是Issue处置动作。提交中只禁当前命令，页面仍可滚动；失败保留草稿，英文错误，版本冲突提示重新加载。

### 9.3 管理台与补件

继续按处理Run列表，不把文件、比较批次、译文伪装成同级记录。新增核对工作流行可展开文件与比较批次；票详情显示当前材料集合及处理历史。

补件入口选择新增／替换，替换明确旧文件和版本；上传成功后显示“新材料尚未纳入上次核对”，提供重核对。新批次发布后刷新当前摘要和状态；旧成功导出记录不被撤销或改写。

### 9.4 五语与异常

系统控件、差异解释模板及状态支持五语；语言选项保留各语种自称；原值、用户意见、原件和译文不随UI切换改写。来源卡按单票→原件／译本分组可折叠，不按每个证据片段生成一个文件卡。

前端明确显示“无可比较对象”“解析中”“关联不明”“核对未执行”“新版本待重算”“当前批次失败”；这些不能显示为零疑点／已通过。轮询和SSE驱动服务端数据投影，禁止界面自造核对完成。

## 11. 重算、导出、问答与生命周期

### 11.1 依赖重算

新增文件仅解析新件，再关联全部冻结有效材料；替换旧件仅重提新版本并失效依赖旧版本的关系；字段纠正只重算相关规则及受影响译段；关系确认只重算受影响组；纯译文编辑不重跑原件跨单证规则，只重跑对应翻译QA与预览。

增量重用需同时验证输入与代码／规则版本。某些全票完整性规则需重跑全部参与清单，不能只检查补件自身。同批关系更新后，即使文件不变也要新批次，不能修改RuleCheck原结果。

首版统一采用“比较依赖变化建新核对Run”，减少同一个冻结Task Spec偷换scope的风险；新Run可复用既有解析和计算，不等于重新OCR／翻译全部材料。

| 变更 | 触发和执行对象 | 旧结果／翻译处理 |
| --- | --- | --- |
| 补件、替换、排除文件 | 上传验收／范围确认只建立新scope和过期提示；点击重核对才建新consignment_check Run | 旧Run和batch保持原输入；若翻译／比较冻结文件集合要变，须新翻译Run |
| 用户确认主体、阶段、货物匹配／改事实 | 确认命令事务建立新scope或业务版，通过同一prepare/start领域服务创建新核对Run并写队列Outbox | 页面显示重核对中；冻结文件／解析／规则范围仍兼容且已采用更新业务／关系依赖时，完成后可追加新binding |
| 纯译文编辑 | 原翻译Run新Epoch，重跑该译段QA和预览；不新建原件比较Run | 对比绑定可保留，复核确认须更新 |
| 同冻结输入执行失败 | W06开启同Run新Epoch并新建attempt batch，parent指向失败batch | 失败batch不改成成功；按成功步骤指纹复用，外部受理不明先核查 |
| 更新规则／Prompt／工作流或改变目标语言 | 建新Run，明确选择新版本 | 不静默升级旧Run；旧快照保留 |

新核对Task Spec冻结scope、Case业务版、文件集合、关系决定、规则／提示词及核对范围；初始batch由Run和epoch唯一分配。重算命令幂等键绑定请求哈希，重复点击返回同Run／batch，不生成多笔作业；数据库事务只写Outbox，后台投递失败可重发，不因HTTP失败重复建Run。每个Case同依赖指纹只允许一个活动核对作业，不同新输入晚到遵循§8.1.1的发布守卫。

翻译Task Spec分别冻结翻译文件集合和比较文件集合，scope ID是首次基线。运行中字段／关系修订可更新业务版和binding，但不得把新文件隐式加进这两个集合。新batch只有文件集合、解析基线、规则／提示词、范围和当前业务版等依赖都与该翻译Run允许范围兼容时才可绑定；否则返回明确不兼容原因，引导新Run，不以“最新批次”强绑。依赖相同的scope修订仅改变无关备注时，可复用已完成批次；复用依据入审计。

### 11.2 导出门禁

新增版本的确认清单冻结：business_revision、translation_revision、preview、scope、batch及binding、规则及Issue有效处置范围。后端原子确认并复核依赖哈希，导出预检再校验一次。

门禁使用§3.6的合并查询：本Run当前译文QA＋活动binding对应的跨单证Issue；冻结每条Issue ID、basis、有效Disposition ID和交付范围判定。`blocks_export`不单独作为陈旧缓存放行／阻断，最终判定由红色、当前未解决、依赖有效、范围适用共同得出。matrix、未解决列表、页头计数和复核清单调用同一个查询投影；处置只推进Case复核状态version，不修改规则原结论。binding缺失／过期属于当前版尚未完成核对，提示重核对而不是虚造红项。

确认后文件／事实／关系发生变化时，仅当前确认失效，旧成功快照不改；新导出需重新确认。黄项和无法判断不硬阻断；未解决且与交付范围相关的红项阻断。忽略关闭当前Issue待办，不改变原件事实；文件不存在、译段为空、版本错配、无权限等技术问题不能忽略绕过。

ExportSnapshot manifest增加scope、comparison batch及关系／匹配ID。证据在工作台可回看，不额外导出复核报告；当前独立核对Run只有业务结果，译本在相应翻译Run导出。

### 11.3 对话与单票记忆

新增受限只读工具：get_consignment_overview、list_comparison_differences、get_comparison_evidence。输入必须来自本轮冻结 `@ `Case／Run／snapshot；客户端或模型提出其他ID时重新授权并拒绝越界。

`@ Case`冻结引用时所选的scope／业务版／成功批次，`@ Run`只读取该Run参与材料及所绑定batch，`@ snapshot`只读manifest固定集合。历史引用不装配当前票新增材料；当前问答发现引用过期时说明“材料已有更新”，经用户明确选用更新范围后重新冻结，不在同回合静默刷新。若原引用登记时作业未完成，续答只补入该登记Run实际产出的batch／解析ID，不追随其他后续Run。

单票摘要保存货物、路线、参与主体、有效材料数、当前批次、差异计数和版本依赖；来源是业务视图，不是模型自行总结后变成事实。旧摘要标过期，回答具体数量／角色仍读取字段和RuleCheck。

用户问“为什么两份文件收货人不同”时自然解释角色和阶段；未确认关系明确说缺少何种依据，不用固定句式，也不强行要求用户先启动翻译。新上传触发识别后按现有continuation机制续答，不能靠摘要掩盖未完成的核对。

### 11.4 删除与隔离

新增表均带tenant_id、case_id，使用同租户／同票组合外键、索引及FORCE RLS。match的所有成员必须属于同Case和冻结清单；拒绝引用其他Case的LineItem，即便同一用户拥有两票也不能隐式并票。

Case删除立即撤权，对话引用、矩阵、历史批次、页图和SSE都拒绝；关系、匹配、批次、绑定、搜索投影、摘要、检查点和新EDI原件纳入现有删除账本及清理顺序。读取时依赖过期不恢复已删除数据。

30天沿用UTC的 `last_material_event_at + 30×24小时`。原件验收／替换、草稿提交或新Run发起、人工修订／处置／确认（含明确关系和范围决定）、成功导出在持有Case锁的业务事务中刷新；同一命令只刷新一次。查询、核对页面打开、问答、候选生成、Worker进度、比较成功发布、失败重试、下载均不刷新。到期立即走现有撤权／清理链，不因后台作业尚未完成延长，也不把历史审计单独永久保留。

## 12. EDI首接方案

候选首接 UN/EDIFACT IFTMIN，目录版本建议 D.01B；上线前必须以实际样本的UNH类型／版本及官方目录核实，未核实不宣布支持该版本。首版只接一条消息，不宣称任意EDI。

处理顺序：原文件上传验证→UNA分隔符和转义→UNB／UNZ、UNH／UNT包络和计数→消息类型／目录版本→段组解析→按限定符映射NAD主体、LOC地点、RFF引用、GID货物、MEA测量等（以锁定目录为准）→字段与结构来源→共享关联／核对。

来源定位为消息号、段序号、元素／分量位置和原始字节范围；EDI阅读视图显示业务表单化结果，点击回到原始段，不伪造PDF页码。严格保留前导零、原小数记法和单位代码。

首次EDI阶段输出识别视图及核对结果；不提供EDI重新发送／回写。若需翻译，后续注册明确的可读译稿模板，标记为业务阅读稿而非原生报文，保留原报文供核验；该格式未有模板时翻译能力位不可用。

新增text/EDI MIME白名单、受控内容嗅探和最大消息／段／长度限制；语法失败保留原件、英文错误说明，不进入伪正常业务数据。恶意长度、未知消息、嵌套附件和字符集异常单独验收。开发不安装新解析依赖，先写小范围段解析器或评估现有依赖；确需新依赖再按项目约定申请。

## 14. 样本与验收标准

### 14.1 代表性样本

第一轮目标至少12票、36份人工标注材料，覆盖四核心类型、五语相关组合、原生PDF／扫描／图片／DOCX、跨页表格与混合文件。先用获授权或合成材料；每类至少3种不同版式，避免只适配演示模板。自动关联达到发布门槛前可增加样本，不以这个最小集推断生产准确率。

样本分开发集和独立验收集，保存正确类型、逻辑边界、关键字段／角色、货物组／阶段、正常差异、真冲突、规则适用和证据位置。合成与真实授权样本结果分别报，不混为供应商宣传准确率。

### 14.2 必测场景

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| A01 | 发票、箱单、提单同货且一致 | 唯一关系有依据；无假红项 |
| A02 | 买方与收货人不同，货代参与交接 | 角色分开，正常差异或待映射 |

### 14.3 发布门槛与性能目标

- 强标识自动匹配：独立验收集不能出现错误自动合并；同时报告样本数、自动覆盖率、准确数、拒判数。有限样本无错不等于生产100%准确；扩大试运行记录后才扩自动规则。
- 四核心类型已标注关键字段：目标精确匹配率≥95%，同时分原生与扫描报告，未达标的格式降为人工确认；测量识别错误与抽取错误分别报告，不删难样本。
- 已标注关键真冲突召回≥95%，正常差异误报率≤5%；核心约束集中的不同角色／单位／分批不得产生硬误拦。阈值是目标，未实测不得写已达成。
- 来源：所有发布红项有当前版双侧可访问证据或明确缺件范围；有可靠坐标的测试锚点必须正确，精度不足明确退化；无虚假高亮。
- 无新增外部解析／模型调用的3–5份、100个明细以内增量核对：目标P95≤2秒；首个任务接受事件目标≤1秒，矩阵首屏API目标P95≤500ms。外部OCR／模型等待单独报告，不承诺整票固定完成秒数。
- 单票当前默认一次最多5份文件。多阶段档案可分次补件；需更多文件的整票核对时先评估Run限制、预算与服务器内存，调整.env并验收，不能仅UI放开。
- 当前生产低并发资源下验证有界内存和聊天分队列响应；不承诺高并发容量。目录范围、样本量、延迟、费用／调用数都进入交付记录。

## 15. 风险、决策与文档联动

| 风险 | 处理 |
| --- | --- |
| 机械按同票、同名、同号合并 | 强标识＋范围＋角色／阶段；歧义候选，保留证据 |
| 只扩菜单，没有格式适配 | 类型能力状态、三种版式样本、提取／定位／核对共同验收 |
| 关系和字段修订污染历史 | 不可变scope、batch、binding；旧Run／快照固定 |
| 模型把材料指令当系统命令 | 提示词注册、材料隔离、受限DTO／工具、服务端决定权限与数值规则 |
| 多匹配组重复计数 | 成员唯一、组范围互斥校验，明确完整性与分配依据 |
| 缺证／HS判断没有生效依据 | 只发布审核版本，条件不足／到期不运行结论，保留来源 |
| 显示已处理但仍无法导出 | 同一批次状态投影，原子确认，门禁原因对应具体对象和版本 |
| 任务重试增加费用或泄漏已删票 | 步骤幂等、OCR原task轮询、删除守卫、取消晚到处理 |

进入X0前需要锁定：代表性样本及许可、首个正式审核规则包的具体范围／专业审核人、IFTMIN实际样本目录版本。前两项中的规则专业审核不能由模型代替；未取得时先做核心单证核对，并把法规包保持未发布。EDI目录未锁定时不阻塞P0。

本文确定的范围／规则／版本语义，在实施前同步需求设计、复核页面设计、后端开发方案及唯一接口契约；实际进度追加X0–X6台账，不覆盖既有D0–D7事实。2026-10-13文档确认阶段仅交付方案，未修改代码、数据库、模型配置或线上服务；2026-10-14实施记录见第17节。
