# F26：识别完成后直接发起翻译

日期：2026-10-14。范围：对话工作台的「发起翻译」入口；不修改后端契约，不重启服务。

## 问题与契约

只读识别完成后，任务卡的「发起翻译」错误绑定了打开上传对话框，导致已有四份原件仍要求重新选择文件。`RunCard` 已支持 indexed 与 checked 两种完成状态，但对话页只为 indexed 提供回调。

沿用 W02 `POST /task-drafts`：创建 `translate_review@2` 草稿，绑定当前 conversation_id/case_id，source_versions 仅来自当前已完成 Run 的冻结清单。目标语言保持未选，由草稿卡确认后再按 W03 启动；本次按钮不直接调用模型或启动翻译。

同票范围通过现有 `GET /cases/{case_id}/consignment-scope` 读取，若已有范围则传入 scope_revision_id；comparison_source_versions 显式限定为当前 Run 来源。后端继续检查范围时效和材料版本，不能默认把其他历史或后来上传材料加入本次处理。

管理台当前「重新处理」仅跳转带 case_id 的上传入口，没有可直接复用的“从 Run 创建草稿”实现，因此仅复用标准 workflowApi，不复制该上传行为。

## 实施

- 以现有 useCommand 管理幂等键、状态与查询失效；用同步锁防止快速重复点击。
- 创建成功后刷新会话及任务草稿，当前任务卡替换为翻译要求表单；请求中显示创建状态，失败保留原任务供重试。
- 识别 indexed 和同票核对 checked 都提供此入口；已结束或归档会话不新建草稿。
- 仅修改 ConversationPage.tsx 必要导入、命令及回调，不扩展其它页面。

已执行现有 TypeScript 编译器 `tsc --noEmit --incremental false`，退出码0；指定文件 `git diff --check` 通过，未跑测试套件、未重启服务。真实浏览器验证由录制主任务执行：识别完成→发起翻译→草稿显示相同四原件，未打开上传框，语言未选、未创建翻译Run；随后确认类型/语言再开始翻译。
