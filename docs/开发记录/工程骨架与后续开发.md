## 本阶段边界

本阶段只建立前后端目录、依赖清单、`.env.example`、配置读取契约、LangGraph 图构造入口、工作流注册表、关键数据契约和可启动的只读健康接口。页面仅展示待开发布局，不接受真实单据或生成处理结果。未安装依赖、未填入密钥、未创建数据库表、未运行 OCR／模型／翻译／导出，也不宣称任何业务能力已经可用。

## 建议实施顺序

1. 经用户同意后建立项目独立 uv 环境、安装锁定依赖；填入真实 `.env`，分别验证对话、抽取、翻译、视觉及 MinerU 接口能力。开发前先补充获授权的小样本与测量条件。
2. 建立 PostgreSQL 领域表、RLS、对象存储访问、Outbox 和检查点初始化；先实现 `read_index@1` 的上传、解析、来源锚点、只读问答和真实事件流。
3. 实现 `translate_review@1` 的规则、译文、QA、人工修订、有效版本配对和复核确认；再实现整组导出、管理台与扩展入口。
4. 每个阶段只跑该模块及直接契约链的测试；故障注入重点覆盖图检查点落后于领域事务、外部任务受理状态不明、对话回合中断及修订后旧结果迟到。

## 开发前必须补齐的验收输入

- 脱敏或合成的图片、原生／扫描／混合 PDF、DOCX 单据样本及可核验字段真值。
- 用户已定四类模型均走 OpenAI 兼容协议；具体服务地址、各角色模型名与 API Key 由用户填本地 `.env`，结构化输出和图片能力仍须实测。
- OCR 首接 MinerU；其接口可用性、坐标／表格输出、请求恢复能力与费用仍须实测，Key 由用户填本地 `.env`。
- 固定的性能测量环境、并发、文件规模与冷／热启动条件。现有 p95 数字只是目标假设。

当前没有运行时依赖锁文件。依赖安装和模型接入完成后，应把实际版本、验证结果和限制回写本记录与[工程技术方案](../技术方案/物流单证智能体_工程技术方案.md)。
