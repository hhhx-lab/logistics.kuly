# 后端开发方案：数据存储与接口

2026-10-08 导出契约：交付物是当前确认版本的纯目标语言译本（所选 DOCX/PDF），可选各原件的识别稿 PDF；不生成复核报告。识别稿从冻结 ParseArtifact 的原文与布局生成，不冒充 MinerU 供应商原始 PDF。一个 Run 对应一个目标语言；其他语言使用各自 Run/确认/快照独立导出，当前不提供多语言一键批量翻译或导出。旧成功快照含报告只作接口兼容，不再展示报告下载；旧失败报告清单在原 Attempt 安全重试时升级为译本与识别稿，历史失败事件保留。

## 0. 开发边界与不可变约束

本方案面向首版桌面优先 Web，采用 Python 3.12、FastAPI、Pydantic v2、SQLAlchemy 2 的 API 请求级 AsyncSession、Celery Worker 独立同步 Session、Alembic、PostgreSQL 16、S3 兼容存储、Celery／Redis 和 LangGraph。用户已经选定四类模型走 OpenAI 兼容协议，解析先接 MinerU；接口适配是否满足结构化输出、坐标和恢复能力须用获授权样本验证。字段模型、文档类型与检索不能锁死一条贸易线路或货类；通用解析、翻译和可说明比较口径的一致性检查覆盖已支持材料，法规／证书类规则仅在已发布规则包的适用范围内执行，未覆盖显示“无法判断”。

1. Case 是一票业务，Upload Session 是一次接收，Run 是固定 Task Spec 的一次处理，ExecutionEpoch 是同 Run 的一次执行，Export Snapshot 是整组回检成功的交付清单。它们不能互相替代。
2. Run 一经创建，参与的 `document_id + document_version`、工作流类型／版本、目标语言、翻译范围和输出格式不可改。改变这些条件建立新 Run；字段修订、重识别与安全重试在同一 Run 留痕并按依赖建立新 ExecutionEpoch。
3. 原件版本、有效解析产物、业务 Revision、译文 Revision、人工处置、确认和成功快照均追加保存。可变的“当前指针”只在同一事务中前移；历史记录、证据和译本始终按冻结版本读取。
4. Run 当前状态与“是否存在成功快照”是两种事实。旧快照成功后当前版再修订，默认已导出列表仍可找回该 Run，同时当前工作版显示待重算／待复核。
5. 所有业务表带 `tenant_id`；业务查询再检查 owner 或 Case 授权。原件、摘要、计数、SSE、深链和下载无例外。对外 ID 不构成权限凭据。
6. 上传中浏览器测得的暂态传输字节与服务端确认接收字节分开；RunEvent、UploadEvent、TurnEvent 分别有自己的递增序号。只有已提交的数据库事件可以作为跨页面和断线后的进度真值。
7. 用户 Skill 仅能调用已注册业务动作；MCP 连接是真实远程工具。扩展、模型或聊天文本均不能直接修改业务事实或审核门禁。

## 2. 关系模型与约束

### 2.1 所有表的共同约定

- 业务表统一使用不可预测 UUID 主键、`tenant_id uuid not null`、`created_at timestamptz not null`；操作者 ID 从服务端认证身份写入，不接受请求体的 `tenant_id` 或 `owner_id`。数据库存 UTC，响应是带时区 ISO 8601；界面用本人设置的时区显示。
- 逻辑主键对外遵循共享契约。源文件用 `document_id + document_version`；Run 参与文件、解析和快照的外键还必须验证同一 tenant、Case 与源版本，不能只检查 UUID 存在。单据短编号只用于展示，不用来关联事实。
- 大字节原件、OCR 原始响应、Markdown 阅读副本、页面图、预览和导出文件进对象存储；数据库存对象元数据、哈希、受控对象 ID 与必要的短原文片段。金额／数量用 `numeric` 和 Python `Decimal`，单号、HS、箱号、电话一律保存字符串及原始写法，不能用浮点或整数吞掉前导零。
- “当前”通过 Case／Run 上的指针或唯一当前投影解析；Revision、解析产物和快照本体不可 `UPDATE` 覆盖。该票有效期内的业务审计只追加，Case 到期或 owner 主动删除时先撤权，再按第 4.4 节清理整票记录、对象版本和检查点；不能把只追加误解为永久留存。
- 对经常按版本读取的子表建包含 `tenant_id` 与父 ID 的复合唯一键，并用复合外键阻止把甲票的区段挂到乙票的解析版本。应用层再检查来源链，不把数据库约束当成唯一授权。

### 2.2 身份、Case 与文件接收

Case grant与账号权限必须同时满足。首版owner行为保持；非owner明确`read`（兼容既有`view`）或`write`才可读取，写入须`write`并通过具体命令所需的账号权限。不能将单独的export_confirm等条目当全写授权。任何写操作等待Case行锁后须刷新实体并重查grant、期限和独立删除账本，阻止锁等待期间撤权后写入。

| 表 | 必须落的列／关系 | 关键约束 |
| --- | --- | --- |
| `tenants`、`users`、`auth_sessions` | 用户登录名、Argon2id 密码哈希、所属 tenant、状态；服务端会话保存随机令牌的哈希、到期、撤销与 CSRF 秘密摘要 | 登录错误不给“用户不存在”之类可枚举信息；会话令牌不明文存库；停用用户立刻失效 |
| `cases`、`case_access_grants`、`case_deletions` | Case 名称、owner、当前业务 Revision 指针、`review_state_version`、独立 `case_version`、`last_material_event_at`、`retention_expires_at`、`active/deleting` 状态；授权表记录主体、能力与期限；删除回执独立于待物理删除 Case 且不能被 Case 的级联删除带走，只保留 tenant/Case ID、发起人、状态、幂等键摘要／请求哈希和必要的清理游标，不保留正文或文件名 | 首版仅创建真实 owner 授权；团队共享 UI 尚未开放但查询入口只认显式授权。当前字段审核、Issue 处置、规则／行匹配投影变化同事务递增 review_state_version，供复核分页防串页；`case_version` 用于整票删除预览的并发前置；Case 清除后 M06 凭回执自身的 actor 校验状态查询与同键重放 |
| `upload_sessions` | Case、发起人、告知版本／确认时间、状态、`next_event_seq`、成功／失败文件数 | 仅告知确认后签发上传；空上传草稿可按保留策略清理 |
| `upload_files`、`upload_events` | 每个所选文件的原名、声明 MIME／大小／哈希、临时对象 ID、状态、已确认字节、失败类；事件 `(upload_session_id, seq)` | 部分失败互不吞并；未通过校验的文件不能变成 DocumentVersion；事件和状态同事务 |
| `stored_objects` | 不可猜键、类别 `temp/source/parse/preview/export`、大小、SHA-256、MIME、创建时间、保留级别、可见状态；正式导出对象在登记前还记录 `finalizing_attempt_id` 与租约截止 | 任何对象都经父资源授权；对象键不出现在 API／深链；`finalizing` 对象不进入正式下载且在有效租约内不被孤儿清理；正式下载只走 API 代理 |
| `source_documents`、`document_versions` | SourceDocument 归 Case；DocumentVersion 记录同一 `case_id` 和所属 SourceDocument，正整数版本、对象 ID、哈希、MIME、页数、上传人／时间 | `unique(tenant_id, document_id, version)`；`(tenant_id, case_id, document_id)` 复合归属由外键约束；补件新 Document，替换才新增同 Document 的版本；旧对象不可改 |

上传 Session 不等于 Run。`upload_files` 成功完成后只新增不可覆盖原件版本；未明确归票、目标语言或处理意图时仍停在草稿，不触发 OCR。浏览器经短期签名上传临时对象时，本机 XHR 进度可连续显示；跨刷新后服务端仅能确认已完成的对象／字节，不把未确认的旧百分比重放成持久事实。

### 2.3 解析、证据与业务版本

| 表 | 必须落的列／关系 | 关键约束 |
| --- | --- | --- |
| `parse_artifacts` | `parse_artifact_id`、源 DocumentVersion、解析器／配置版本、原始响应对象 ID、Markdown 对象 ID、质量状态、时间 | 同源重识别新增行，不改 DocumentVersion；只有有效解析产物可供新业务版引用 |
| `logical_documents`、`document_sections` | 均绑定同一个 `parse_artifact_id`；逻辑单据类型候选／确认标志；区段原页／原区域、顺序、所属逻辑单据 | 混合 PDF 能有多个 LogicalDocument；未解析文件无这两类行；区段不能跨 ParseArtifact |
| `source_segments`、`source_anchors` | 片段短文本、结构类型、页／段／表／单元格、定位精度、可用矩形及坐标系、源 LogicalDocument 和 Section | 对外锚点精度与契约统一为 `rect/page_only/paragraph_only/cell/none`；`rect` 才有真实 bbox，DOCX 渲染页码必须带渲染版本；禁止猜框 |
| `field_assertions`、`line_items`、`line_match_edges` | 原文值、规范值与单位、字段角色、行数据、来源锚点；人工采用值以新的不可变断言／裁定记录引用原始断言 | 同一来源链完整；跨单据行匹配用多对多边和依据，不按行号硬配 |
| `business_revisions`、`business_revision_fields`、`section_assignment_decisions` | Case 内版本号、创建原因／操作者、当前有效 FieldAssertion 引用、人工类型或区段归属覆盖 | `unique(tenant_id, case_id, revision_no)`；原始解析候选不覆盖；新版复用未变断言，当前指针以 compare-and-swap 前移 |
| `section_scope_mappings` | 针对 `selected_sections` Run 保存冻结选区的旧 `parse_artifact_id/section_id`、同源新版 `parse_artifact_id/section_id` 集、实际支持映射的锚点、语义范围核验结果、可选 InputRequest、确认人／时间 | 只在相同 DocumentVersion 内追加不可变映射；旧 Task Spec 引用不改写。证据不足则保持待确认，不把相似标题当映射；新范围扩大／缩小须新 Run |
| `resolved_translation_scopes` | 每 Run／解析版的不可变必译源段集合、未译源段集合、范围模式、`goods_description` 选择器版本、实际货描字段／行及来源、人工确认记录与指纹 | `all` 覆盖可读全文，`selected_sections` 依冻结选区，`goods_description` 依 `cargo_description@1` 角色选择器；零命中或含糊时必须 W05 `translation_scope` 请求，不凭标题猜范围；重解析后只按可核验证据映射，不静默扩缩 |
| `field_review_events` | 对当前版本的“确认无误／无法判断”动作、原因、所见来源、操作者／时间 | 确认字段不等于裁定红项；这类审核状态变更无需伪造新原文字段，仍要重新评估确认门禁 |
| `artifact_dependencies` | 派生产物 ID、实际读取的源版本／断言／片段／规则／术语／模板／提示词版本与指纹 | 仅让依赖变化的规则、译段、预览、摘要、索引过期；不因 Case 版本号改变就全票重复 OCR |

源片段和字段须有 `(tenant_id, case_id, document_id, document_version, parse_artifact_id, logical_document_id, section_id)` 的可验证归属链。人工确认类型或把区段划给另一逻辑单据时，保留 ParseArtifact 的机器候选，写 `section_assignment_decisions` 和新的 Case 业务 Revision；复核查询按所选业务版读取有效归属，历史深链继续按旧版解释。若重解析改变了区段或行 ID，先写映射或标为待复核，绝不凭文本相似自动复用旧锚点和裁定。`selected_sections` 的映射由 `section_scope_mappings` 记录来源证据和人工决定，只能把新解析结果解释为原冻结范围的等价呈现；未确定时以 W05 `document_boundary` 请求暂停重译和确认。

### 2.4 Run、人工输入、复核与交付

| 表 | 必须落的列／关系 | 关键约束 |
| --- | --- | --- |
| `task_drafts`、`runs`、`run_documents` | 草稿保存 Case、有序源版本、`workflow_type/version`、类型化 `draft_parameters`、三态澄清状态、`draft_version`、选区解析基线、可空 `discarded_at/started_run_id`；Run 保存 `draft_task_id`、不可变 Task Spec JSON 与 SHA-256、冻结 Prompt Registry 版本清单、发起人、当前状态／阶段、当前 Epoch、最近事件序号；参与文件表保存有序的固定 DocumentVersion 集 | 未启动草稿只能写 `discarded_at` 软撤销，TaskDraftView 活跃状态仍只取 `needs_clarification/ready/unsupported`；W03 锁草稿并比较版本及解析基线，启动时同事务写 `started_run_id`。`runs(tenant_id,draft_task_id)` 唯一且关联同 tenant 草稿；草稿撤销不删 Case、UploadSession 或已验收原件，Run 输入集合不可改 |
| `execution_epochs`、`step_executions`、`step_reconciliations`、`model_migrations`、`queue_outbox` | Epoch 目的、冻结业务／解析输入、非秘密 ModelBinding、Run 冻结的 Prompt 版本、图版本；步骤指纹、状态、`step_version`、租约令牌／截止、外部请求键／任务 ID、尝试和产物；运营核查结论、模型迁移记录；待投递消息 | 队列仅传 `run_id + epoch`；普通新 Epoch 继承原 Run 的 Prompt 版本及当前批准的模型绑定，只有 O02 的显式受控记录可迁移模型绑定；Prompt／工作流契约升级另建 Run。旧租约持有者提交时被栅栏拒绝；领域提交与 RunEvent 同事务 |
| `input_requests` | Run、类型 `document_boundary/source_language/translation_scope`、冻结输入／解析版本、可空的期望业务版、问题与可选答案、状态 `active/resolved/superseded/cancelled`、回答者、答案、解决时间 | 同 Run 最多一条活动请求；`document_boundary` 可在字段抽取和首个 BusinessRevision 前发出，resolve 对 `expected_business_revision_id=null` 必须核对当前仍无业务版，同时核对解析版；`translation_scope` 仅确认冻结货描语义的实际源段；`awaiting_input` 时图结束并释放 Worker。仅明确新 Run 替代或 R11 使旧解析源失效且有审计动作时可标 `superseded`；R11 在同事务结束旧活动请求后才允许新请求，单次 `NEW_RUN_REQUIRED` 错误不自动结束旧请求 |
| `run_events` | `(run_id, seq)`、阶段、状态、时间、文件／页、可读消息、可靠计数、版本变化或快照 ID | 同事务分配 seq 并写业务状态；SSE 只复播这些行，不用 Redis 消息充当历史 |
| `rule_checks`、`issues`、`issue_dispositions` | 检查版本、输入来源、适用性与 `passed/failed/not_applicable/not_covered/undetermined/not_run` 原始结果；Issue 严重度、源 A/B、交付阻断；人工处置、依据、操作者／时间 | `not_covered` 是规则包没有覆盖该情形，`undetermined` 是适用规则已运行但证据不足；两者分开计数、说明和评估门禁，均不伪装为通过。原件冲突原结论不被裁定改成“通过”；缺证红项不能用无依据接受绕过 |
| `translation_revisions`、`translation_segments`、`translation_compatibilities`、`preview_artifacts` | 译文归 Run／语言，按源片段引用，不可变版本；QA 和有效配对；预览对象及渲染版本、草稿／过期状态 | 纯译文编辑只增本 Run／语言译文版；未变依赖可用兼容记录配新业务版；旧预览坐标不投新稿 |
| `review_confirmations`、`export_attempts`、`export_attempt_items`、`export_snapshots`、`export_artifacts` | 确认冻结 Run 范围 `review_fingerprint`、Task Spec、原件／解析／业务／译文与 RuleCheck、IssueDisposition、FieldReview、行匹配、QA／预览的有效 ID 集／摘要及输出格式；Attempt 保存同一指纹、`queued/rendering/checking/failed_retryable/failed_final/succeeded/paused_reconcile` 状态、最近失败类、确认 ID 与逐文件／识别稿 PDF 渲染回检项、暂存对象归属／大小／哈希／保留期；成功快照 manifest 及每源文件选定格式与所选识别稿 PDF | 成功 Snapshot 每个参与 DocumentVersion × 选定格式恰一正式产物，另所选逐源识别稿 PDF；历史复核列表按冻结 ID 集读取，未全通过绝无新快照。同 Run 同指纹的未结清 Attempt 必须按原 Attempt 恢复，不因更换确认 ID／幂等键再建；失败不自动抹掉仍有效的 ReviewConfirmation |
| `idempotency_records`、`audit_events` | actor、scope、键、请求哈希、结果 ID／响应摘要、状态；审计记录动作、对象、所见版本、时间和 trace ID | 相同键同内容返同结果，异内容拒绝；日常只能追加，归档不删审计；整票到期或主动删除时按已定 30 天策略清除该票关联记录，另留不含票据内容的最小删除回执 |

Run 的状态机至少含 `queued、processing、awaiting_input、awaiting_review、ready_to_export、exporting、exported、indexed、paused_reconcile、failed_retryable、failed_final、cancelled`；合法边由领域服务枚举并定向测试。`indexed` 仅属于 read_index；`ready_to_export/exported` 仅属于 translate_review。导出 Attempt 安全失败而确认版仍有效时，Attempt 标 `failed_retryable`、Run 回 `ready_to_export`，由 R15 的定向 retry 继续同 Attempt；W06 的 Run retry 仅管非导出工作流步骤。确认版失效则 Attempt 标 `failed_final` 并记录 `REVIEW_STALE`、Run 回 `awaiting_review`；外部受理不明则 Attempt 与 Run 均 `paused_reconcile`，先 O01。任何失败都不能写成成功 Snapshot。`paused_reconcile` 只能由有运营核查权限的命令解除，普通 `retry` 不得越过。

### 2.6 必须由数据库兜底的唯一性与归属

迁移不能只建表而把核心不变量交给 Python 的先查后写。至少落下列约束，跨表复杂门禁仍由锁定事务中的领域服务核对：

| 不变量 | 数据库约束与事务校验 |
| --- | --- |
| 同源版、同 Run 输入不重复 | `document_versions(tenant_id, document_id, version)` 唯一；`run_documents` 带 `case_id`，`(tenant_id, run_id, document_id, document_version)` 唯一，并分别以 `(tenant_id, case_id, run_id)` 与 `(tenant_id, case_id, document_id, document_version)` 复合外键验证同票归属。Task Spec JSON／哈希和已创建的 RunDocument 集合由禁止更新触发器或等价数据库权限冻结，不仅依赖路由层约定。 |

## 3. PostgreSQL 迁移、RLS 与索引

### 3.1 迁移顺序与发布方式

以 Alembic 版本链创建：① tenant／auth／Case 与授权；②对象元数据、上传与原件；③解析、来源、业务 Revision；④Run、Epoch、步骤、InputRequest、事件与 Outbox；⑤规则、Issue、译文、复核与导出；⑥会话、搜索、扩展与设置；⑦查询优化索引和种子记录。每一批建表同时建约束与 RLS，开发环境和生产环境都只能走迁移。`pg_trgm` 在索引迁移前由部署数据库启用；若环境不可用，启动就绪检查明确报告，不能悄悄把大规模模糊检索退化为无界全表扫。LangGraph Postgres checkpointer 的初始化／版本迁移是独立步骤，只由部署命令在 API／Worker 启动前执行，不能让所有实例同时调用 `setup()`。

迁移采用“先扩展字段／表，双读兼容，回填，最后收紧约束”的发布次序。正在执行的旧工作流版本由旧、新 Worker 均可读取；新 Run 只有在注册定义及其表结构部署齐全后开放。不得对历史 `TaskSpec`、Snapshot 或旧解析版本做原地 JSON 改写来迎合新代码。

### 3.2 RLS、认证引导与授权

应用与 Worker 的数据库角色不持有 `BYPASSRLS` 或 DDL 权限。每个业务表启用并强制 RLS；策略为 `tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid` 的 `USING` 与 `WITH CHECK`，未设置上下文即失败关闭。每次 FastAPI 请求或 Worker 业务操作开始显式事务后先 `SET LOCAL` 当前 tenant，再做任何业务查询；连接回池后不残留会话级设置。跨租户外键含 tenant_id 或在写服务中以同等强度验证，运行查询必须同时检查 owner／Case grant 和操作能力。

登录和会话核验发生在 tenant 上下文建立之前，应放在隔离的 auth schema，以窄权限认证函数／专用认证连接完成令牌哈希查找和 Argon2id 校验；仅返回本次认证主体 ID、tenant ID、会话状态，不开放业务表的无租户查询。普通 Worker 队列消息按基线仅含 Run ID 和 Epoch，须通过仅授予 Worker 的窄权限解析函数取得该 Run 的 tenant_id，然后在租户事务内重新读取 Run 与 Epoch；删除 Worker 只凭删除作业 ID 经另一窄权限函数取得其 tenant_id，再设置事务级 RLS 上下文并复核作业状态。不能为方便队列处理给 Worker 全库直读或默认 tenant，完成删除后 Case 行不存在也不影响最小回执鉴权。

本地账号使用随机、可撤销的服务端会话。Cookie 为 HttpOnly、Secure、SameSite，写命令校验 Origin 与 CSRF token；Vite 开发环境用同源代理 `/api`，避免生产跨域 Cookie 语义和浏览器 S3 地址不一致。所有列表、数量、搜索建议、SSE 每次重连、文件代理每个 Range 请求均重新校验主体；旧浏览器缓存不得回退展示撤权正文。权限矩阵最少分查看、发起、修订、裁定、导出确认和运营核查；首版单用户演示也应由真实账号和显式角色执行，不用“系统自动确认”。

### 3.3 必建索引与查询计划

| 查询 | 索引起点 | 定向验证 |
| --- | --- | --- |
| Case／Run 授权与状态 | `cases(tenant_id, owner_user_id, created_at desc, id)`；`runs(tenant_id, case_id, status, created_at desc, id)`；`run_documents(tenant_id, run_id, document_version_id)` | 同票多 Run 不复制原件；状态查询不扫解析正文 |
| 上传和事件补齐 | `upload_events(tenant_id, upload_session_id, seq)`、`run_events(tenant_id, run_id, seq)`、`turn_events(tenant_id, turn_id, seq)` 唯一 | 断线从 N 取 N+1，不漏且不重 |
| 最新／历史成功快照与最近导出失败 | `export_snapshots(tenant_id, run_id, exported_at desc, id desc)`；`export_attempts(tenant_id, run_id, created_at desc, id desc)`；`export_artifacts(tenant_id, snapshot_id, document_version_id, format)` | 最新快照和最近命中旧快照按同一冻结版打开；管理台失败页能找到 Run 已回 `ready_to_export` 的最近失败 Attempt |
| 角色字段及日期 | `search_field_values(tenant_id, projection_id, role, normalized_value)`；`search_projections(tenant_id, run_id, snapshot_id, logical_document_id)`；上传／发起／复核／导出日期列 B-tree | 默认同一 LogicalDocument 与同 Run 任意文件产生可解释的不同命中 |
| 模糊文件名／编号／摘要 | 归一化文本的 `GIN ... gin_trgm_ops`；候选查询先 tenant／Case 授权且 `LIMIT 8` | 用真实中文文件名、地名与单号做 `EXPLAIN ANALYZE`，必要时再调归一化规则 |
| 步骤恢复与幂等 | `step_executions(tenant_id, run_id, step_name, input_fingerprint) WHERE status='succeeded'` 有效结果唯一；`queue_outbox(status, next_attempt_at)`；`idempotency_records(tenant_id, actor_id, scope, key)` 唯一 | 跨 Epoch 复用相同输入产物；租约与供应商幂等／查询能力可证实时安全去重，不明受理状态转 `paused_reconcile` 而不自动重付费 |

索引只针对确有页面查询的列建立；大对象文本不全量放进 PostgreSQL。管理台分页采用稳定的 `(sort_time, run_id)` 或 `(sort_time, snapshot_id, run_id)` 键集游标，游标签名并绑定用户、筛选哈希、展示版本范围和查询水位；默认建议 25 行，`@` 候选先限 8 行。用户读第 3 页时新事件只提示“有更新，刷新列表”，前端不重排当前结果。对工作版状态变化须保存可按水位读取的投影版本或查询会话结果，不能只在游标里写时间却查询实时可变行而声称绝无漏项／重复项。

## 4. 对象存储、上传和受控下载

### 4.1 对象命名与可见性

对象存储保持私有桶。服务端管理凭证只给 API／Worker，不进前端构建变量。内部服务地址与浏览器可达的上传地址可能不同：Compose 中 `minio:9000` 仅容器可见，应通过同源反向代理公开受限上传路径，或在 `.env` 增加经实测的公开 S3 地址并正确设置 CORS；签名时使用浏览器实际访问的 Host。所有新配置须在 `.env.example` 用中文说明用途、获取方式和必填性。`/data-processing-disclosure` 的 OCR／模型服务显示名从已发布的非秘密部署配置取得，不从模型 ID 或 URL 猜供应商。

对象键由服务端随机生成，按 tenant、Case 与类别分前缀，用户文件名只能进元数据和经过清洗的下载名，不拼接进对象键。`source`、`parse`、`preview`、`export` 使用不同前缀和生命周期；每次写新键，不原位覆盖。单票正式原件、成功快照及其业务审计按第 4.4 节的 30 天 Case 期限统一清理；暂存、失败上传和无引用孤儿可更早按受控短期生命周期清理。先在 `stored_objects` 记录暂存意图，实际 PUT 后核验哈希／大小，再登记为可见对象；数据库提交失败留下的孤儿对象由清理器按“无引用且超过安全等待期”回收。普通孤儿清理先反查 `document_versions`、`parse_artifacts`、`preview_artifacts`、`export_artifacts`、`export_attempt_items`，不能回收仍运行／可重试／待核查 AttemptItem 或有效 `finalizing` 租约引用的对象；**整票删除**先撤权、使这些任务不可继续，再按清理清单删除它们，不适用“只删无引用对象”的普通孤儿规则。

### 4.2 从告知到 DocumentVersion 的逐文件流程

1. `GET /api/v1/data-processing-disclosure` 返回告知版本与变更时间，并逐项列出当前发布的 OCR、模型和文件存储服务的显示名、用途、可能外发的数据类别、实际部署区域、已核实的外部保留／删除口径与是否启用，同时说明本地 Case 最后实质性变更后保留 30 天及主动删除范围；显示名和区域取已发布的非秘密部署配置，禁用项不得写成正在使用。供应商留存不能满足 30 天边界时真实单证入口不得宣称可用。界面在**任何文件字节离开浏览器前**让用户确认。服务端把告知版本、确认人、时间和配置摘要写入 Upload Session。服务配置改变后旧告知版本不能签发新文件上传凭证。
2. `POST /api/v1/cases` 创建草稿 Case；`POST /api/v1/cases/{id}/upload-sessions` 验证 Case 发起权限、文件数、名字长度、格式声明和单文件上限。若带 `replace_document_id`，先检查它确属该 Case 且所见 `expected_document_version` 为当前版；补件不带替换 ID。然后为每个文件创建 `upload_file_id`、位于受控 tenant/Case/UploadSession 暂存前缀且带随机不可猜后缀的临时对象键和短期上传策略。返回每文件独立的上传信息；不因某文件失败取消其他文件。签名 PUT 的声明大小不等于对象存储已强制限长；浏览器可达的上传网关还须设置请求体上限、并发与速率限制，U05 再按对象实际字节数拒绝超限并清理临时对象。
3. 浏览器以 XMLHttpRequest 或等价可测上传 API 直传临时对象。进度百分比来自该浏览器这次请求已发送字节／文件总字节，只是临时传输状态；服务端 `upload_files.confirmed_bytes` 在单次 PUT 模式下仅于完整校验后变成文件大小。刷新后未完成的传输显示“待确认／可重试”，不重播上次本地百分比。若样本证明必须跨刷新续传，再引入 S3 Multipart 与已确认分片表，接口仍保留“签发／完成／重试”的同一业务语义。
4. `POST /api/v1/upload-files/{id}/complete` 用幂等键取得该文件的完成租约，先核对 Upload Session 和 Case 仍可写、告知版本有效，再从对象存储 HEAD／流式读取临时对象：比较实际字节数和 SHA-256，检查文件魔数与声明 MIME、允许的 PDF／图片／DOCX 格式、压缩包展开大小、宏和外部引用风险、页数或可在上传时验证的结构限制。不能只相信浏览器报告的哈希、文件后缀或 Content-Type。
5. 校验成功后先短事务锁 Case／UploadFile，重查 `active`、期限、删除栅栏与替换所见版，登记带截止时间和对象键的 `finalizing` 归属租约；事务提交后才将临时对象复制到不可覆盖的 Case 前缀原件键并复核大小／哈希。复制结束再短事务锁 Case，重查栅栏、租约与 `expected_document_version`，然后锁定 SourceDocument（替换时）或创建它（补件时）；冲突则不登记原件，标记刚复制的对象待删，保留上传槽供用户重新选择。通过后写 DocumentVersion、`stored_objects` 可见状态、上传状态和 UploadEvent，更新成功数，并记录操作者。替换同一 Document 的版本在锁内取 `current_version + 1`，旧版本只读；重识别不会走这里。事务提交后才给前端“已接收”与 `document_id + document_version`。对象复制成功而数据库提交失败时只留待清理的孤儿，不给业务原件入口；删除清理器须等待该票的 `finalizing` 租约结束或到期，并在最长对象写入超时后复扫前缀，不能先报 `completed`。
6. 校验失败时在该 UploadFile 写错误类与 UploadEvent，保留成功文件；`POST /upload-files/{id}/retry` 只为失败或未确认文件重新签发临时对象键／上传策略，旧待清对象隔离。`POST /upload-files/{id}/cancel` 只取消尚未完成的传输，不能借此删除已接收原件或影响 Run。重复文件哈希只对当前用户有权范围内的文件给提示，并要求“保留／移除”选择，不跨用户去重。

文件已接收不等于解析完成；上传接口不得在同步 HTTP 请求里调用 MinerU 或模型。`GET /api/v1/upload-sessions` 按本人可见 Case、状态、创建时间与游标列草稿，并只统计有权项；`GET /api/v1/upload-sessions/{id}` 及其事件流给当前 Session 的逐文件状态、服务端已确认字节、错误类、可用动作及 `last_seq`，为对话托盘和管理台“上传草稿”共用。上传部分成功时启动 Run 只能使用请求明确选中的已接收版本；失败文件不能混入固定集合。

### 4.3 文件、预览与正式交付读取

所有原件、页图、净化的 DOCX 阅读结构、双语预览、草稿预览下载、识别稿和正式 ExportArtifact 均有**经过父资源鉴权的 API 读取入口**。原件 PDF／图片与正式产物使用后端分块代理支持 HTTP Range：每次请求重新验证会话、Case、版本、Run／Snapshot 归属，检查请求字节范围，返回 200／206／416 的正确 `Content-Range`、`Accept-Ranges` 和受控 Content-Type；设置 `Cache-Control: private, no-store`、`X-Content-Type-Options: nosniff` 与清洗后的 `Content-Disposition`。DOCX 原件只按附件下载或使用服务端净化的段落／表格阅读 JSON，不把未知 DOCX 内的 HTML、宏或链接直接内联执行。预览只有绑定的 `preview_version` 仍存在且有权时可读；历史预览已清理则返回“已过期”，不能把旧译段坐标套在新预览。

正式下载只从成功 ExportSnapshot 的 manifest 中查 ExportArtifact，再取对象。下载中断再次请求同一 artifact，不重跑导出；管理员撤权后新 Range 请求即时拒绝。浏览器永不接收 S3 管理凭证、不可撤权的长期 GET 签名地址或对象键。深链只保存受控 ID 与版本。对象存储复制桶、版本、生命周期、备份和可能阻止删除的 Object Lock 均纳入部署清单；若受控原件在复制端或锁定版本无法按整票期限清理，不得接入真实客户单证。

### 4.4 30 天留存与整票删除

`CaseRetentionService` 把 `retention_expires_at = last_material_event_at + 30 × 24h` 作为唯一口径，所有时间存 UTC。新 Case 创建时起算；成功原件验收／替换、TaskDraft 提交或 Run 发起、人工修订／处置／确认、成功 ExportSnapshot 登记属于实质性业务变更，在锁 Case 的同一事务更新 `case_version、last_material_event_at、retention_expires_at`。普通查询、下载、对话问答、Worker 阶段事件和失败重试不刷新期限。到期扫描器以 `FOR UPDATE SKIP LOCKED` 选到期且 `active` 的 Case，锁后重查期限，复用主动删除的领域入口；并发业务写若先提交新期限，扫描器跳过，删除若先置 `deleting`，业务写一律拒绝。每个 Case 读写入口、Worker 步骤提交和对象代理读取都检查状态与期限；定时扫描延迟也不能让到期 Case 继续可读。

M06 预览给 Case 所有人展示原件版本／Run／成功快照计数及当前 `case_version`；POST 带该版本、幂等键和整票确认标识。事务内校验 owner 后锁 Case，版本变化给 `CASE_CHANGED`；成功则置 `deleting`、递增执行栅栏、撤销授权、从搜索与 `@` 投影移除、写不含正文的 `case_deletions` 清理作业和 Outbox；独立删除账本确认记录该提交后才返回 `202`，确认延迟则保持不可读并允许同键重试。此时所有 Case 业务 API、SSE、Range、已打开的对话续答与新上传签名立即拒绝；已有短期 PUT 只能写隔离暂存键，U05 必须拒绝登记原件。幂等重放先按同一 actor 的最小删除回执返回原作业；其他用户不得凭 ID 探知是否存在。会话因一会话只绑定一票而整体清理，用户已确认的通用偏好保留但移除该票来源指针，未确认的票据记忆建议直接清理。迟到的 Worker 必须因 Case 栅栏失败而只留下可清理孤儿，不能重新生成 RunEvent 或 Snapshot。若返回给浏览器的内容流已在删除事务提交前开始，代理必须在每段发送前复查撤权栅栏并中止后续字节；无法实现该中断语义时只能用有短有效期且不含正文的读取令牌分段取数，不能把整票内容一次性预取后在删除后继续发送。

`CasePurgeWorker` 使用只可按已登记 deletion_id 清理对应 tenant/Case 的专用数据库角色，不依赖已撤销的普通 Case grant，也不授予业务 API 通用 `BYPASSRLS`。清理器按固定清单分批、幂等且可恢复地清除：UploadSession 与临时键、所有 DocumentVersion 和原件对象版本、解析原始响应／Markdown／页图、业务与译文版、Issue／RuleCheck、预览、ExportAttempt/Snapshot/Artifact、摘要与检索投影、Case 绑定的会话／续答／扩展调用和挑战、对应幂等与业务审计、`checkpoint_refs` 指向的 LangGraph 线程及其检查点。对象存储若开启版本控制，必须删除**所有 object versions 和 delete markers**；按 Case 受控前缀再扫无元数据孤儿。先登记待删对象及线程清单和清理游标，再实际删除；隔离暂存区中删除前已签发且仍有效的 PUT 可能在首次扫描后才落对象，因此至少在最后一枚签名过期、该票上传／导出 `finalizing` 租约与最长在途对象写入时限结束后再扫一次并设独立暂存 TTL，不能先标清理完成。确认对象与关联行均已消失后把作业标 `completed`，最后仅留不含票据正文、文件名或对象键的最小回执供原发起人查询，并保留 actor＋Case ID＋幂等键摘要／请求哈希以便 Case 行消失后同键重放；回执至少留到作业完成且最长备份窗口结束，之后按独立最小账本策略清理；中途失败保持 `deleting` 并由受权恢复器重试，不回滚访问权。主存清理的目标上限为请求或到期后 24 小时；上传签名有效期须短于此上限，清理失败须报警并持续不可读。加密备份最长保留 7 天；删除事务把最小删除标记与 `deleting` 状态原子写入 PostgreSQL；部署须把包含该事务的 WAL／变更记录以可核验连续序号同步到**独立于主库恢复快照**的加密删除账本（只含 tenant/Case ID、请求时间、状态），不把普通异步双写当原子保证。未确认该账本已收录删除提交前，不向客户端承诺删除已完成；Case 已置 `deleting` 时仍保持不可读，同键请求可查最小回执。账本至少保留到所有删除前备份过期；恢复须先核对连续序号并重放删除命令，缺失则停止对外服务，先清理被删 Case 再开放服务；只恢复主库内旧 `case_deletions` 表不足以证明安全。第三方 OCR／模型若不能以协议或删除能力保证不超过已披露的 30 天留存及主动删除要求，本系统不能对真实单证宣称满足该策略；上传告知必须标明外部数据去向与期限。

## 5. API 服务层逐模块实现

### 5.1 每个路由共同执行的管线

路由只做请求解析、认证与响应映射，实际业务在服务层。统一顺序是：① 为请求生成 `trace_id`；② 从 HttpOnly Cookie 解析真实用户和 tenant，检查 CSRF／Origin（写操作）；③ 进入数据库事务并设置 `SET LOCAL app.tenant_id`；④ 按 Case 和动作检查权限、`active` 状态与 UTC 期限，解析所有外部 ID 的归属；⑤ 对命令锁定幂等键和期望版本；⑥ 调用领域服务，由领域服务维护状态和事件，若属第 4.4 节实质性业务变更则同锁更新 Case 期限／`case_version`；⑦ 提交事务后通过 Outbox 通知异步工作；⑧ 将共享契约的 DTO／错误封套返回。读接口也须建立 tenant 上下文，不能“只是读取”就跳过权限；到期扫描延迟不构成继续提供原文的理由。

对外错误码、响应字段和 HTTP 状态以共享契约为准。实现至少区分：未登录、无权／不存在、入参错误、同键不同内容、同一会话上一 Turn 未完成、版本冲突、Task Spec 改动须新 Run、复核门禁阻断、外部请求待核查、服务未就绪和限流。错误详情只给当前用户有权看到的当前版本、缺项和可执行动作，不泄露另一用户对象是否存在。写命令用 `Idempotency-Key`；`idempotency_records` 的唯一键为 tenant＋actor＋动作作用域＋键，请求的规范化 JSON 算 SHA-256。首次执行在事务内锁键；已完成且哈希相同返回先前结果，哈希不同返回冲突，仍在执行则返回已有操作 ID／状态。幂等记录只存受控结果 ID 和小响应，不存原件正文。

下列表格中的“返回”只说明服务需要提供的业务真值，字段命名与错误封套以共享契约为准。只读查询均需明确 `snapshot_id` 或当前工作版语义；可选过滤和游标必须先绑定当前身份再查询。

只读识别问答采用异步续答。C04 的 Turn／用户消息先提交；内部 `start_read_index_for_turn` 使用该 Turn 的稳定幂等键，在**同一个短领域事务**中创建或关联有权且输入完全一致的 `read_index@1` Run，锁定该 Run 行，再同时登记 `AssistantContinuation(parent_turn_id, question, source_versions, run_id)`、真实首轮说明消息、`message_final` 与 `continuation_pending` TurnEvent、Turn `completed` 和所需 Outbox。只有该事务提交后才释放单回合锁并允许续答消费者写事实消息；崩溃重放按 Turn／Continuation 唯一键回读，不补造第二个 Run 或第二条首轮说明。关联既有 Run 时也先拿同一 Run 行锁：若已 `indexed`，首轮说明为“识别已完成，正在核验来源”并在本事务立即投递续答；若是 `failed_retryable/paused_reconcile`，同事务记 `awaiting_retry/awaiting_reconcile` 和可见 `continuation_status`；若已 `failed_final/cancelled`，同事务记无事实的 `continuation_final`；仍在运行才显示“正在识别”。

Run 进入 `indexed/failed_retryable/paused_reconcile/failed_final/cancelled` 的领域事务也先锁同一 Run 行，再逐条更新已登记待答项及其 TurnEvent／Outbox。于是“先注册后到终态”由状态转移唤醒，“先到终态后注册”由登记事务立即处理；`failed_retryable/paused_reconcile` 保留续答资格，W06/O01 恢复后重置 `waiting`，到 `indexed` 再唤醒，只有 `failed_final/cancelled` 终结。需要同时写会话消息时遵循 Run → Continuation → 会话序号的锁顺序，首轮说明提交前不得发事实续答。续答消费者以 Continuation 独立租约、尝试计数和下次尝试时间执行；租约过期后重验输入与授权再领，安全瞬态失败退避重试并持久发布 `continuation_status`，超过上限或不可恢复错误置 `failed` 并发 `continuation_final`，不让页面永久旋转。续答只用原问题、冻结源版及本次索引实际产出的 ParseArtifact／业务版／证据 ID，使用 `continuation:{id}` 独立图线程；不读取期间新消息或别的会话摘要。若会话已结束只记 `closed` 与新会话追问入口，权限撤销只记 `restricted`；最终证据答复的消息 ID、Run 与 parent_turn_id 留痕，按 `(continuation_id, indexed_artifact_set_hash)` 去重，不计第二用户轮次。

| `GET /api/v1/runs/{id}/events` | 验权后从 RunEvent seq 游标补齐并持续读取；只发已持久化事件，连接撤权后停止 | 任务卡、校验概览、管理台时间线共享同一事件及实际计数 |
| `POST /api/v1/runs/{id}/cancel` | 锁 Run，检查可取消状态及当前收费步骤；递增执行栅栏，写取消请求／事件并由 Worker 在安全边界停止。已发外部调用且提交状态不明时进 `paused_reconcile`，不立即声称 cancelled；历史 Snapshot 不删除 | 排队显示“取消处理”，运行中显示“请求取消”；按最终持久状态刷新 |

| `GET /api/v1/runs/{id}/input-requests`、`POST /api/v1/input-requests/{id}/resolve` | 解析后边界／类型、源语言混排或货描实际源段范围无法可靠确定时，Worker 写 InputRequest、`awaiting_input` RunEvent 并正常结束本次图。三类为 `document_boundary/source_language/translation_scope`：前两类分别处理逻辑单据边界／重识别映射与冻结范围内的语言，第三类只让用户在原定 `goods_description` 语义下确认源段候选。用户回答时锁 Request＋Run，核对冻结原件、`expected_parse_artifact_id`、可空 `expected_business_revision_id`、请求版本和答案 schema；业务版期望为 null 时要求当前仍为 null，不能把“无版”当成跳过前置条件。只确认既有 Task Spec 范围内的分类／语言／实际货描源段，写决策、必要的新业务版或 `ResolvedTranslationScope`、Request 终态、RunEvent、新 Epoch 与 Outbox 同事务 | 对话卡显示明确问题与选项；回答后同 Run 继续。若答案改变参与文件或冻结翻译范围，返回 `409 NEW_RUN_REQUIRED` 与可预填草稿，不原地改 Task Spec；同一请求重复回答按幂等键返原结果 |

`read_index` 的结果发布索引与来源后进入 `indexed`；不能运行翻译规则、产出译文或 Export Snapshot。`translate_review` 按其固定图运行到 `awaiting_review`；人为复核等待由 Run 持久状态承接，Worker 不跨天占用 LangGraph `interrupt()`。InputRequest 同理；回答后新 Epoch 从领域版本及有效产物指纹继续。新工作流未来只通过注册定义、TaskSpec schema、图版本、UI 合同、规则和验收样本接入；本组上传／Run／事件 API 不复制。

当前 `src/backend/app/router/contracts.py` 骨架仍只有 `selected_section_ids`；实施 W02/W03 前应把它替换为带上述完整解析归属链的 `selected_section_refs`，并由同一 Pydantic 判别联合生成 OpenAPI／前端类型。本段是实施要求，本轮不把骨架视作已经满足契约。

`awaiting_input` 的活动请求是当前边界或语言的唯一写入口。`resolve` 在锁住 Request、Run 与所见业务版后，先核验该请求仍为活动、答案属于候选且不越过 Task Spec，再原子写回答与决策。相同目标的普通 `sections/{id}/assign`、`sections/{id}/confirm-language` 即使带新版本也返回 `409 INPUT_REQUEST_ACTIVE`，不能让人工绕过等待卡而保留一条悬空请求；若 Request 已被撤销或版本过期，前端重新读取 W05 后再操作。请求已解决、Run 不再等待时，普通区段命令才按 R09 的期望版本和权限执行。

### 5.5 各类人工命令与版本影响

所有复核写命令都必须有幂等键、所见 Case 业务版／相关 Run 译文版及目标自身版本；服务端在事务内锁当前指针和目标，核对权限及输入归属后重新计算依赖。版本变化返回当前值和允许前端展示的差异，禁止旧表单覆盖。`POST /api/v1/cases/{case_id}/change-impact/preview` 是纯计算：用当前 ArtifactDependency 图估算拟编辑字段／区段／译段会使哪些规则、译段、QA、预览、摘要、索引和其他 Run 过期，不写业务表、不调用模型；保存时必须重新计算，不能把预览结果当放行凭据。

| 独立命令 | 事务中要写什么／不能写什么 | 后续动作与页面反馈 |
| --- | --- | --- |
| `POST /api/v1/cases/{case_id}/fields/{field_id}/confirm` | 校验字段及原文锚点属于所见业务／解析版且有权查看；追加 FieldReviewEvent（确认人、所见版本、时间），不改原文或人工采用值。红 Issue 是否已裁定不作为字段原文确认的前置 | 字段标“已人工核对”，但 Issue 仍独立阻断；必要时使旧 ReviewConfirmation 不再是当前确认 |
| `POST /api/v1/cases/{case_id}/fields/{field_id}/mark-unknown` | 记录无法判断原因、需要资料与操作者，并关联／建立对应 Issue；原字段候选仍保留 | 门禁按具体字段用途和规则重评，不能把“无法判断”视作通过 |
| `POST /api/v1/cases/{case_id}/fields/{field_id}/revise` | 新建不可变人工 FieldAssertion／Decision 和 Case 业务 Revision，compare-and-swap 当前指针；保留机器原值、理由及补充依据引用 | 同事务标记受影响规则、译文、预览、摘要、搜索投影和当前确认过期，写 RunEvent／Outbox；不重跑未受影响 OCR |

| `POST /api/v1/documents/{document_id}/versions/{version}/reparse` | 验证当前可处理原件和费用／权限，锁 Run 与该文件的活动 W05；若有旧解析版请求则同事务标 `superseded`、写原因和事件，旧 resolve 随即拒绝，再创建同源版的新解析执行批次及 Outbox；不新增 DocumentVersion、也不立刻替换有效 ParseArtifact 指针 | 新解析产物通过来源校验后再建业务版并失效相关依赖；如仍需人工确认，新解析完成后按同 Run 活动请求唯一约束发新 W05；其他 Run 若依赖旧解析也标需核对，历史快照不变 |

### 5.6 复核确认、整组导出和快照下载

`review_fingerprint` 由 R13/R14/R15 共用一个纯领域函数计算：在同一授权 Run 的一致性快照上，按稳定 ID 顺序规范化序列化固定 `task_spec_hash`／源版本、当前与本 Run 有关的有效解析、逐源 `resolved_scope_refs[]`／选区等价映射 ID 与字段断言／审核事件、RuleCheck 的适用性／结果与规则版、Issue 处置、行匹配、逐源业务／译文／Compatibility 配对、QA 与必需 `reading_html` 预览版本及所选输出格式，再取 SHA-256。可选草稿 PDF 是否可下载不进入确认门禁。不得把 Case 的裸 `review_state_version`、时间戳、列表计数或其他 Run 的变动当作指纹输入；Case 业务 Revision 前移但本 Run 实际依赖未变时，须按 ArtifactDependency 的有效输入集与兼容记录证明配对等效，确认不应误失效。指纹输入清单随确认冻结，便于重算和审计；`not_covered` 与 `undetermined` 按各自原因和已发布门禁策略分开计算，未覆盖必须出具未覆盖说明，关键事实缺证不能因规则未覆盖而放行。

字段／译文或解析后来发生变化时，新工作版确认失效，Run 可回到 `processing/awaiting_review`；旧 ReviewConfirmation 和旧 Snapshot 不回写或删除。Snapshot 级摘要、问题和正式产物永远读取其冻结版本；管理台已导出行即使当前工作版待复核，也可以把旧交付标“历史”并提供显式“查看当前版”。

### 5.8 Skill、MCP、本人偏好与记忆

此模块拆为三个服务：`ExtensionRegistryService` 给仓库和对话 `/ ` 候选提供同一版本化注册事实；`McpConnectionService` 管真实远程连接与调用门禁；`UserPreferenceService` 只管当前登录者的设置和已确认偏好。每条写命令沿用 5.1 的认证、幂等、期望版本和审计管线。内置“单据任务路由”由代码注册、普通用户只读；仓库里的名称和文字说明不能生成额外 Python 节点或越过已注册业务动作。

## 6. 事件流、事务和恢复

### 6.1 数据库事件是唯一进度真值

`upload_events`、`run_events`、`turn_events` 各自独立按所属 UploadSession、Run、Turn 的 `seq` 递增；不同操作的 seq 不能拼成一条全局时间线。领域服务在更新状态／产物的**同一事务**里先原子增加父行的 `next_seq`，再插入事件。事件至少含操作 ID、Case、时间、阶段、状态、可选文件／页、版本、错误类、用户可读说明，以及仅在分母可靠时出现的已完成／总量。纯模型步骤不编造百分比；阶段完成事件必须在对应产物可查询后才提交。Redis、Celery 和 LangGraph 内部 stream 只用于投递或唤醒，不作为断线历史。

前端按“先快照，后订阅”加载：`GET /runs/{id}`／`GET /upload-sessions/{id}`／Turn 创建结果带 `last_seq`，SSE 首次可用 `after_seq=last_seq`，浏览器自动重连时用 `Last-Event-ID`；服务端始终查询数据库 `seq > cursor ORDER BY seq`，因此快照和订阅之间的新事件不会丢。原生 EventSource 无法自定义请求头，初次游标允许 query 参数；如果 header 与 query 同时存在，采用已校验的较新游标并按该单一操作范围解释。客户端只按 `operation_id + seq` 去重，事件缺口时再取快照和遗漏事件，不用客户端时间排序。

SSE 不应持有一个跨几分钟的数据库事务：每次短查询重新建立 RLS tenant 上下文、核对授权、取批次事件，然后释放连接；无新数据时以数据库通知或有限间隔轮询等待，并发送不含业务正文的心跳。反向代理关闭响应缓冲，设置 `text/event-stream` 与 `Cache-Control: no-store`；断开后任务继续。权限撤销、会话失效或 Case 删除后下一轮检查立即关闭流，不能依靠初次握手时的授权一直发送。过久的游标若事件已按保留策略清理，返回明确的“需重取快照”信号，不能安静跳到最新阶段。

### 6.2 命令、Outbox 与 StepExecution 的提交顺序

所有写命令使用短事务；外部 OCR／模型／对象存储网络调用绝不在持有 Case 行锁的事务中等待。以字段修订为例，顺序为“锁 Case 当前版 → 验证 expected 版本与权限 → 插入不可变新断言和 Revision → CAS 更新当前指针 → 标过期摘要/依赖/确认 → 写受影响 RunEvent → 插入唯一 Outbox → 提交”。Outbox 发布器在事务提交后把 `run_id + execution_epoch` 交 Celery，并把投递结果记回账本；发布器崩溃或重复投递均靠唯一键和 Worker 领域租约去重。

Worker 读取 Run 的固定 Task Spec 与 Epoch，取得 `lease_token`、`lease_until` 并持续续租，使用 `run:{run_uuid}:epoch:{n}` 的内部检查点线程 ID；普通新 Epoch 使用该 Run 冻结的 Prompt 版本及当前批准的 ModelBinding，只有 O02 记录可改变后者。Celery prefork 子进程启动后独立初始化同步 SQLAlchemy Engine/Session、同步 Postgres checkpointer 和 `httpx.Client`；不能继承父进程或 FastAPI 的 AsyncSession／异步客户端。领域步骤先以 `step_key + input_fingerprint` 查有效产物，已有结果则直接返回其 ID。准备外部收费调用时，先在 StepExecution 持久化确定性 `provider_request_key`、模型／提示词／适配器版本与 `submitting` 状态，提交事务后调用供应商；若支持幂等请求键则传递，若支持按键查询则恢复时先查。拿到 `external_task_id` 立即落库；回包经 schema／来源校验后再在短事务里以租约令牌、Epoch、Case `active` 和未到期状态及指纹作栅栏，把对象 ID、结果、费用及 RunEvent 一同提交，**最后**返回图节点，让 LangGraph 写检查点。

若“领域事务提交成功，图检查点尚未写”时进程崩溃，图节点重执行从 StepExecution 读回既有有效产物，不再收费；若“供应商已受理但本地任务 ID 未存”且供应商不能凭请求键查询／去重，不自动重投，StepExecution 进 `needs_reconcile`，Run 进 `paused_reconcile`。租约过期不代表供应商未执行。2026-10-16新增的模型传输中断策略在存活调用内默认最多3次实际请求（含修复），退避2秒、4秒，逐次记录`interrupted`与未知费用，耗尽进入`failed_retryable`并复用成功产物；不会把旧未知回执伪报未受理。OCR未知提交、进程崩溃和账本失败仍按前述核查规则处理。安全瞬态错误也受同一配置次数与总时限控制；参数错误、源文事实冲突、无法定位来源不以重试模型掩盖。Run 取消时增加执行栅栏，旧 Worker 的晚到结果可作为旧输入诊断记录，但不得恢复当前状态或生成 ExportSnapshot。恢复扫描器只投递未确认 Outbox、租约超时且可证明安全的步骤，以及已完成核查准许重投的步骤；另按 `next_attempt_at` 扫描 `waiting` 或租约过期的 `running` Continuation，在原 Run 状态与授权仍允许时重领独立续答租约，不重新收费解析，也不重复首轮消息。

同一 Case 的并发修订按锁顺序“Case → Run（按 ID 稳定排序）→ 当前字段／Issue → 相关摘要／事件”执行。Run 读当前版本时在单个事务内拿到一致的版本指针；不能先读字段再从另一个请求读译文而拼成不成配对的 UI。当前版指针 CAS 失败返回版本冲突，旧表单保留草稿；不通过“最后写入者获胜”覆盖人工裁定。对话同会话同时只允许一个活跃用户 Turn；后台 Run 和 `AssistantContinuation` 不占用户新回合锁。续答以 `AssistantContinuation` 自身的租约和幂等键运行，图检查点用 `continuation:{continuation_id}` 或等价独立只读答复服务，不能与正在执行的新 Turn 共用 `conversation_thread_id`。续答消息提交时才短暂锁会话消息序号，写前再次核对会话未结束、Case 授权与原引用版本；已写成功的 continuation_id 与索引产物指纹阻止重复。

## 7. OpenAPI、前端联调和错误可操作性

FastAPI 每个公开路由都声明 Pydantic v2 请求／响应模型、权限依赖、错误响应与 `operation_id`；`/api/v1/openapi.json` 是前端生成 TypeScript 类型的输入。对外时间为带时区字符串，金额与精确数量传十进制字符串，UUID 为字符串，来源锚点用带 `kind` 的判别联合，`null` 明确表示尚无版本或尚无译文，不能填虚构 ID。Run 状态、Issue 结果／处置／交付门禁、预览有效性和快照是否成功分别用独立字段，避免前端从一种徽标推断另一种事实。SSE 事件虽然是流，也用同一 schema 的判别联合文档和契约样例，前端解析失败应显示连接错误而非把未知事件当完成。

错误响应需包含稳定错误码、`trace_id`、字段路径、当前用户可见的冲突版本或阻断项，以及下一步可执行动作。版本冲突返回“所见业务版／译文版 vs 当前版”和可读取差异的受控 ID；不提供其他用户数据。Run 卡片、复核按钮和管理台菜单使用服务端 `allowed_actions` 与 `disabled_reasons` 渲染，但服务端接到命令时仍重查权限和门禁。`/health/live` 只表明进程存活；另设就绪诊断检测数据库迁移、对象存储、Redis、图检查点与模型／MinerU 接入的实际配置和探测结果，前端从 `/workflows` 的可用性决定入口，不因 liveness 200 就让用户发起必然失败的任务。

联调先用固定的脱敏或合成一票三文件材料，逐条沿同一个 Case ID 和 Run ID 追踪：对话主卡上传 → Task Draft → read_index／translate_review → SSE → 复核深链 → 修订失效 → ReviewConfirmation → ExportSnapshot → 管理台 → 新会话 `@`。对每个前端可点动作，在 OpenAPI/共享契约中能找到对应读或命令；反向检查每个后端动作都由明确控件、系统恢复器或运营页面触发，不留下“前端能点却只能修改假数据”的路径。前端不得直接连 PostgreSQL、Redis、MinerU 或模型端点。
